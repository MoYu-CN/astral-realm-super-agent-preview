# 安全边界：出站守卫与工作留痕

> 一句话：**出去之前先问人，进来之后留下话。**
> 前者防的是「AI 把我们自己的密钥、身份证、客户名单送出去」；
> 后者防的是「活是别人派的，出事却说不清」。

版本：schema v10　·　2026-11-11　·　对应代码 `electron/security/`、`electron/memory/security.js`

---

## 1. 两个场景，两套装置，不要混

| | 出站（往外发） | 派活（往里进） |
| --- | --- | --- |
| 触发 | AI 要调用会往外送东西的工具 | 有人 @ 你、单聊你、点名安排事 |
| 危险 | 隐私 / 凭证 / 客户数据流出，收不回来 | 事情做了，但没有证据是谁让做的 |
| 装置 | **闸门**（security_gates） | **账本**（security_ledger）+ 任务（security_tasks） |
| 用户看到 | 一个确认框：「这段内容要发出去吗」 | 一条候选：「这像派活，要不要留痕」 |
| 默认 | 命中就问，密钥级默认「不发」 | 不记账，等你点头 |

两套装置共用一条原则：**决定权在用户，装置只负责把决定记录下来。**
它不替用户判断「该不该发」，也不替用户判断「这活该不该接」。

## 2. 闸门：出去之前先问人

### 2.1 什么算出站

| 场景 | exposure | 处理 |
| --- | --- | --- |
| 内置工具（写文件、读文件、查记忆、截屏） | `none` | 不问。写自己硬盘不算外泄 |
| 外部工具，名字像「发 / 传 / 提交 / 建工单」 | `send` | 命中就问 |
| 外部工具，名字像「列 / 查 / 读 / 搜」 | `pull` | 只在密钥 / 身份级命中时问 |
| 外部工具，名字认不出来 | `unknown` | 按 `send` 算，宁可多问一次 |

名字不可全信，但也不能不信：`list_issues` 与 `create_issue` 只差一个动词，
所以先看动词、再看名词；名字里同时带 `send` 一类动作词的，一律按能发算。

### 2.2 识别什么

| 类型 | 级别 | 判定方式 | 为什么这么判 |
| --- | --- | --- | --- |
| 私钥 | 密钥级 | `-----BEGIN … PRIVATE KEY-----` | 出现即事故 |
| API 密钥 | 密钥级 | 固定前缀 + 长度：`sk-` `ghp_` `AKIA` `AIza` `xoxb-` `glpat-` `sk_live_` … | 前缀是厂商给的，几乎不会误报 |
| 口令字段 | 高危 | `password:` `密码：` `token=` 后面跟 ≥6 位 | 比裸串可靠：有键才有值 |
| 身份证 | 高危 | 18 位 **且校验位算得过** | 只按「18 位数字」判，订单号会天天报警 |
| 银行卡 | 高危 | 16–19 位 **且 Luhn 通过**，排除全同数字 | 同上 |
| 手机号 | 敏感 | `1[3-9]` + 9 位，前后不接数字 | 工单号、时间戳不会撞 |
| 疑似密钥串 | 敏感 | 24–64 位、至少两类字符、非纯 hex、前后 48 字内有 key/token/密钥 | 纯 hex 一律不报：git 哈希每天出现几十次 |
| 本机路径 | 轻微 | `C:\Users\…` `/Users/…` `/home/…` | 只提示，不拦 |

**误报比漏报更毁这件事。** 一天弹二十次「你确定要发吗」，第三天用户就闭眼点允许了，
边界等于没有。所以每条规则都要能用真实样本解释，且都带一个「不报」的对偶条件。

### 2.3 放行规则

```
risk = none                      → allow
exposure = none（不出本机）        → allow
exposure = pull 且 risk ≤ 敏感     → allow（只取不送）
risk 命中 且 属于已放行的类型       → allow（只对中低风险，8 小时）
其余                              → confirm（开一道闸门，等人点头）
```

**密钥级内容永远逐次确认。** 「这类不再问」对 `critical` / `high` 不开放：
可以容忍「手机号这半天别问了」，不能容忍「API 密钥这半天随便发」。

### 2.4 批准绑在指纹上

```
digest = sha256(kind | target | 正文或参数规范化 JSON)
```

- 批准一次 = 这个 digest 在 30 分钟内可用一次；
- 改一个字、换一个群、换一个工具 → digest 变了 → 重新问；
- 用掉即作废（`status = used`），再来要重新批。

这条设计的好处是：不需要把批准令牌发给 AI。AI 手里没有凭据可偷，
它只能「再检查一次」，而检查会去库里找有没有同指纹的批准。

### 2.5 库里不存正文

闸门表只三样东西：**指纹、脱敏预览、命中清单**。

- 预览：`对方让我把这个发过去：sk-pro…Yz`；
- 命中清单：`[{type, level, label, count, samples:[脱敏], where}]`；
- 正文一个字节都不落库。

理由很直白：为了安全先把用户的密钥收一遍存起来，是这类功能最容易闹的笑话。
数据库被拖走时，攻击者拿到的是「某人曾试图发一个 sk- 开头的密钥给产品群」。

## 3. 账本：派活留下话

### 3.1 一条留痕的一生

```
消息进来 → 分流为 alert → 像派活？ → 建候选（不写账本）
                                        ↓ 用户在界面上点「开始留痕」
                                   账本第 1 条：任务来源（谁 / 哪条渠道 / 原话 / 时限）
                                        ↓ AI 每做一步
                                   第 n 条：动作（工具 / 目标 / 摘要）
                                        ↓ 外发被拦
                                   第 n 条：拦下（闸门编号 / 风险 / 去向）
                                        ↓ 用户批准
                                   第 n 条：批准（谁批的 / 范围）
                                        ↓ 做完
                                   最后一条：归档（结果 / 证据位置）
```

**候选阶段账本是空的。** 留痕是用户的决定，不是系统的：
被丢掉的候选一条记录都不留（只留一个 `dropped` 状态，证明「当时问过、你说不用」）。

### 3.2 只追加的两道锁

1. **数据层**：`security_ledger` 上的触发器直接 `RAISE(ABORT)` 掉 `UPDATE` / `DELETE`；
2. **数学层**：每条的 `hash = sha256(prev_hash + "|" + 规范化 JSON)`。

改一行，它自己的哈希对不上；删一行，下一行的 `prev_hash` 接不上。
`verify()` 从头重算整条链，报出第一个断点——不抽样、不信任索引。

写错了怎么办？**追加一条 `correct`**，而不是改上一条。这是账本，不是文档。

### 3.3 存证包长什么样

`security_ledger action=export` 或界面上的「导出存证」产出一段 Markdown：

```markdown
# 工作留痕 · A-20261111-01

- 留痕编号：A-20261111-01
- 建立时间：2026-11-11 19:44
- 任务来源：企业微信 · 产品群 · 张经理
- 时限：明天下午三点
- 状态：已归档
- 结论：方案已发出，对方回复收到

## 原始要求

> 小王，麻烦你明天下午三点前把方案整理一份发我

## 时间线

| 时间 | 类型 | 谁 | 内容 | 哈希 |
| --- | --- | --- | --- | --- |
| 2026-11-11 19:44 | 任务来源 | 用户本人 | 来自 张经理 · 时限 明天下午三点 · 原话：… | 3f9a2b7c1d |
| 2026-11-11 19:46 | 动作 | AI | write_text_file → 方案-v1.md | 8c1e… |
| 2026-11-11 19:47 | 拦下 | AI | 产品群 · 密钥级 · 闸门 G-… | 2b7d… |
| 2026-11-11 19:48 | 批准 | 用户本人 | 产品群 | 91af… |
| 2026-11-11 19:52 | 归档 | 用户本人 | 方案已发出，对方回复收到 | 5d0c… |

## 责任链

- 这件事是 张经理 在 2026-11-11 19:44 提出的，原话见上。
- 期间执行动作 3 次，外发 1 次，用户批准 1 次。
- 每一次外发都对应一次明确批准，批准绑在具体内容与具体去处上。

## 完整性

- 账本条目：12
- 本任务条目：5
- 链头哈希：`a4963e9fdf32…`
- 校验结果：通过（从头逐条重算，全部一致）
- 校验方法：第 n 条的 hash = sha256(第 n-1 条的 hash + "|" + 本条规范化 JSON)。
- 账本由数据库触发器禁止修改与删除，只允许追加。
```

### 3.4 它证明什么、不证明什么

必须说清楚，否则「免责」两个字就是在骗人。

**能证明**

- 某条消息在某个时刻、从某条渠道、由某个人发出，原文如此；
- 某个动作在某个时刻由 AI 执行，参数是什么；
- 某次外发得到过用户本人的明确批准（或没有）；
- 这份记录自建立以来没有被修改、删除、插入。

**不能证明**

- 记录**完整**。只有「记下来的都真」，没有「真发生的都记下来了」——
  如果一开始就没开留痕，账本是空的，它不会替你补。
- 原话的真实性。账本保证「你记的和当时一样」，不保证「对方当时确实这么打字的」——
  那需要平台侧的存证。
- 法律责任划分。它是**证据材料**，不是判决；到底谁担责，仍要看合同、职责与法律。
- 图片与附件内容。只记「有几个附件」，不解析里面写了什么。

把这几条写在导出件里、写在界面上，比多喊几句「放心」有用。

## 4. 压缩、首流与追原委

账本是证据，事件是索引。归档那一刻，账本一条不动，事件网里多一行 ——
这样「记得住」和「记得细」才不打架：日常回忆只碰事件，追责时才翻账本。

### 4.1 压什么、不压什么

| | 账本 `security_ledger` | 事件 `events`（前缀 `LZ`） |
| --- | --- | --- |
| 条数 | 一条不留 | 一件留痕一行，最多几行 |
| 内容 | 原话、每一步、每次批准 | 谁（渠道·会话）：原话前 62 字 → 结果前 42 字 |
| 用途 | 导出存证、逐条校验 | 检索、权重排序、进上下文 |
| 可改 | 触发器禁改禁删 | 可合并、可重建索引 |

- `summary ≤ 150` 字，`result ≤ 120` 字：`动作 2 · 外发 1 · 批准 1 · 拦下 1 · 账本 7 条 · 证据 A-…`。
- **先脱敏再落库**：原话里可能夹着密钥、身份证；事件会被检索、会进上下文，
  留痕不能反过来成为泄露渠道。
- 幂等：账本没长出新的条目就不重复写；有新条目再压，追加下一条（同一任务可有多条）。
- 编号 `LZ001`，系列「工作留痕」，`project_id` 为空 —— 留痕是跨项目的，不挂到某个项目下。
- **不进时间网**：它是「被派活之后发生的事」，不是作息习惯。混进去会让时段里多出一个
  只在出事时才出现的系列。

### 4.2 首流：只回答两件事

常驻上下文末尾多一小块 `### 安全状态（实时）`：

```
- 待你点头 1 件：密钥级·产品群
- 在办 2 条：A-20261111-01 把方案整理…
- 已归档 5 条，进事件网 3 条
- 问原委：security_ledger action=trace id=A-20261111-01
```

只回答「现在有没有事等着你决定」和「问原委去哪儿问」，上限 260 字，不搬账本正文。
四块硬性上下文的 3600 字预算不变；这一块约 100–200 字，单独计算。

### 4.3 权重：四个因子相乘，随时能解释

```
weight = (0.42 + 0.58·evidence) × (0.6 + 0.4·integrity)
       × (0.65 + 0.35·severity) × (0.7 + 0.3·freshness)
```

| 因子 | 怎么算 | 为什么 |
| --- | --- | --- |
| evidence | `1 - 0.5^(条数/5)` | 空候选 0，5 条 0.5，15 条 0.87 |
| freshness | 半衰 120 天 | 责任追溯比知识衰减慢，半年前的账仍要能翻出来 |
| integrity | `0.35 + 0.35×批准覆盖率 + 0.2×已归档有结论 + 0.1×已进事件` | 批得齐、有结论、有索引的更可信 |
| severity | `0.25 + 0.18×min(2,拦下次数) + 0.25×是否密钥级` | 被拦过的、密钥级的更该先看 |

示例：空候选约 23% · 6 条账本 + 1 次批准 + 1 次拦下约 60% · 同样的记录放到 240 天前约 43%。

### 4.4 追原委：按时间排，不按重要度排

`security_ledger action=trace`（编号或一句话都行）返回六段：

```
【来路】谁、什么时候、在哪条渠道哪个会话、原话、时限
【做了什么】每一步：谁做的、什么类型、结果
【结果】归档时写的那句话
【证据】留痕编号 · 事件编号 · 账本条数 · 权重 · 链是否完整与链头
【同一时间前后】同网 0.5 + 内容 0.3 + 同时段 0.2，窗口默认前后 12 小时
【要留意】账本是空的 / 没归档 / 外发与批准对不上 / 有更正
```

- 有编号用编号；没有就按一句话找。**问原委时按权重与时间，不要求字面重合**
  （用户说的是「谁让我改合同的」，原话里可能只有「合同」）；普通问法只认内容。
- 相关事件靠事件网的连边、内容重合、时间接近三样加权，能带出「那会儿你也在改另一个项目」。
- 原文只在这里出现：这是用户发起的回查，不是日常注入。
- 记录缺口照实说。原委不是故事会，缺哪段就说缺哪段。

## 5. 接到哪里

| 入口 | 行为 |
| --- | --- |
| 主进程工具调用（`astral:mcp:call`） | 外部工具执行前先过闸门；命中就弹**原生确认窗**，默认按钮是「拒绝」 |
| `security_check`（MCP 工具） | AI 自己先查一遍，`verdict=confirm` 就停下来告诉用户，别硬发 |
| `security_ledger`（MCP 工具） | `tasks / open / append / close / ledger / verify / export / digest / trace` |
| `security_check` 的 `brief` | 首流那一小段状态，两三行 |
| 收件箱入库（`inbox.ingest`） | alert 且像派活 → 自动建候选 |
| 设置 → 安全边界 | 待确认队列、留痕（含「看原委」「压进事件」）、账本、校验、导出、两个开关 |
| `astral:security:*`（IPC） | 10 个通道，`decide` 只认主窗口 sender；`task` 的 `trace` 走只读 |

**「完全授权」跳不过闸门。** 工具授权回答的是「这个工具能不能用」，
闸门回答的是「这段内容能不能出去」——两件事，两个开关。
`permissions.full = true` 的用户照样会在密钥外发时被问一次。

**AI 批准不了自己。** `approve` / `deny` 只存在于主进程 IPC，
且校验 `event.sender` 必须是主窗口；工具层（`security_check`）没有这条路。

**面板批准 ≠ 工具放行。** 在设置页点头，批的是「这份内容可以发」；
真到调用外部工具时，主进程还会在原生窗里再确认一次。两次之间不共享凭据——
凭据只在主进程内存里签发，AI 手里没有可偷的东西。代价是极少数情况下多一次点击，
换来的是「没有任何一条路径能让 AI 自己把密钥送出去」。

## 6. 看不见的地方

这份清单要主动写出来，不然用户会以为「开了守卫就万事大吉」。

1. **工具自己去读的文件**。闸门看的是调用参数；如果工具的参数只是一个路径
   （`read_file("C:\\Users\\me\\.env")` 然后发走），闸门看不到文件内容。
2. **截图与图片里的密钥**。目前不做 OCR。
3. **用户自己手动发**。用户在聊天框里复制的，不经过闸门——那是他自己的决定。
4. **已经被授权「这类不再问」的内容**。手机号在 8 小时内不再问，这是用户选的。
5. **端到端加密的第三方通道**。闸门只看得到交给工具的明文参数。
6. **账本的完整性**。见 3.4。

对应的缓解不是「假装能拦」，而是：默认最小权限、每次外发留一条账本、
以及把上面这些原话写在设置页的说明里。
