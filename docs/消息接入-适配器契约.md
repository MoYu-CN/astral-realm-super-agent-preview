# 消息接入 · 适配器契约

> 这份文档定义「一种渠道要满足什么，才能被接进来」。核心、数据库、界面都不认平台，只认这套契约。
> 新增一种渠道 = 在 `electron/intake/catalog.js` 加一条 + 在 `adapters/` 加一个实现，其余不动。

## 1. 为什么要有契约

渠道之间差异极大：企业微信是加密 XML 回调，OneBot 是 WebSocket 长连接，微信个人号是本地加密库，
手机通知是一行文本。如果每个渠道各自往数据库写，会出现三件事：

1. 去重逻辑各写一遍，于是同一条消息能被记三次；
2. 分流规则散在各处，于是「为什么这条提醒我」永远说不清；
3. 加一种渠道要改五处代码，用户看到的界面也跟着分叉。

所以把「拿到」和「怎么办」分开：适配器只负责拿到并翻成统一形状，剩下全部由收件箱那一层处理。

## 2. 渠道描述（catalog.js）

```js
{
  id: 'qq-personal',
  label: 'QQ · 个人号',
  vendor: 'QQ',
  summary: '一句话说清它能给你什么',
  transport: 'websocket',            // local-db | callback | websocket | http
  risk: 'risky',                     // safe | caution | risky
  scope: ['private', 'group'],
  capabilities: {
    receive: true,                   // 能不能收
    send: false,                     // 能不能代发
    history: false,                  // 能不能拿历史
    realtime: true,                  // 是不是实时
    mentions: true                   // 能不能识别 @
  },
  timing: '实时（WebSocket 长连接）',
  note: '风险与限制，直接给用户看',
  fields: [ /* 配置项，见下 */ ]
}
```

`capabilities` 是给界面用的：用户看卡片就知道这条渠道能给他什么，而不是被文案糊住。
`risk` 不只是免责声明，它是排序依据——界面上永远按 safe → caution → risky 解释。

### 字段定义

| type | 说明 | 落盘位置 |
| --- | --- | --- |
| `text` | 普通文本 | `config` |
| `number` | 数字，非法值回落到 default | `config` |
| `boolean` | 开关 | `config` |
| `select` | 枚举，`options: [{value,label}]` | `config` |
| `path` | 本机路径 | `config` |
| `password` | 密钥，**`secret: true`** | 加密存储，不进 `config` |

`required: true` 的字段没值就拒绝保存，错误信息里会列出缺哪几项。

密钥走 `secret-box.js`（Electron `safeStorage`，Windows 下是 DPAPI）。取不到 safeStorage 时退化成
base64 并在界面上标「未加密」——不假装加密了。

## 3. 适配器接口

```js
{
  passive: false,                    // 是否依赖我们的 HTTP 入口
  async start (ctx, channel, secrets) → { ok, status, error?, env? }
  async stop  (channelId)             → { ok }
  status      (channelId)             → { running, ... }        // 可选
  async send  (ctx, channel, secrets, target) → { ok }          // 可选，只有声明了 can.send 才用
  async callback (ctx, channel, secrets, req) → { status, body } // 被动渠道用
  parse       (channel, body, query) → [raw]                     // HTTP 渠道用
  authorize   (channel, secrets, headers, query) → { ok }        // HTTP 渠道用
  async detect(channel) → { ready, ... }                         // 可选，环境自检
}
```

`ctx` 只给三个能力，防止适配器越界去碰数据库：

```js
ctx.ingest(channelId, raws)      // 交给收件箱（归一化、去重、分流都在那边）
ctx.setStatus(channelId, 状态, 错误)
ctx.saveCursor(channelId, 游标)
```

适配器**不许**直接写 SQLite，也不许自己判断「要不要提醒」。它只有一个职责：把外面的事情翻译成 `raw`。

## 4. 统一消息形状

`normalize.js` 会把这些字段压成一条记录：

| 字段 | 说明 | 缺省 |
| --- | --- | --- |
| `text` | 正文；纯附件也要给个占位 | 必填（或带 attachments） |
| `scope` | `private` / `group` | `group` |
| `chatId` | 会话标识（群 id / 对方 id） | `default` |
| `chatName` | 会话名 | 群用 id，单聊用对方名 |
| `senderId` / `senderName` | 谁说的 | 空 |
| `msgId` | 平台消息 id | 空 |
| `at` | 时间（秒/毫秒/ISO 都认） | 现在 |
| `mentionsMe` | 是否 @ 了我 | false |
| `attachments` | 附件数 | 0 |

**去重键**：`sha1(渠道 + 会话 + msgId + 分钟 + 发送人 + 正文前 64 字)`。
有 `msgId` 时不用时间，避免同一条消息重复推；没 `msgId` 时把时间压到分钟，
于是「同一分钟重复推」只算一条，跨分钟仍算两次（转发告警本来就该算两次）。

## 5. 分流

分四档，规则在 `normalize.js` 的 `RULES`：

| 档 | 含义 | 后续 |
| --- | --- | --- |
| `alert` | 有人在叫你 | 可以弹一条 |
| `observe` | 该记下来（约时间、托办事、吃喝） | 进观察池，到点再问 |
| `knowledge` | 像是一条经验 | 沉进知识网 |
| `archive` | 其余 | 只归档，不打扰 |

判档的关键**不是分数，是「有没有人在叫你」**：@、点名、命中用户自设关键词、或出现「在吗 / 尽快 / 速回」。
一堆闲聊凑到高分也不弹窗。没人叫你，再热闹也最多进观察池。

只有 `alert` / `observe` 会写 `observations`——归档的东西不该影响时段习惯与进程阶段。

## 6. 微信个人号的桥接约定

个人微信没有官方接口，读本机库又要处理 SQLCipher 与 WCDB。我们**不打包任何解密工具**，
只定义桥接契约，用户自己选工具，或者换工具。

两种后端：

### 6.1 命令（首选）

```bash
<命令> --since <ISO 时间或 0>
```

stdout 每行一条 JSON：

```json
{"chatId":"123@chatroom","chatName":"项目群","senderName":"老张","text":"明早十点开会","time":1731000000,"scope":"group"}
```

- 只输出 `--since` 之后的消息；没有新消息就输出空。
- 失败就把原因写到 stderr 并以非 0 退出，状态栏会显示出来。
- 程序自己负责解密与增量，我们只消费 JSONL。

### 6.2 chatlog 服务

本机跑着 chatlog 的 HTTP 服务时填地址（默认 `http://127.0.0.1:5030`），
适配器会先读 `/api/v1/session` 拿会话，再按会话拉 `/api/v1/chatlog`。
字段名做了容错：`talker / talkerName / isChatRoom / content / createTime` 都能认。

### 6.3 纪律

- **原件只读**：只在副本上工作，任何时候删掉副本不影响微信。
- **图片不硬啃**：微信 4.x 的 `.dat` 是 AES，目前没有公开解法，只存占位。
- **结构探测**：大版本升级表结构会变，探不到就降级成「只读文本 + 告警」，不静默失败。

## 7. 新增一种渠道要改什么

1. `electron/intake/catalog.js` 加一条（能力位、风险、字段）；
2. `electron/intake/adapters/<name>.js` 实现 `start/stop`（或 `parse/authorize`）；
3. `electron/intake/index.js` 的 `adapters` 表里登记一行；
4. 跑 `npm run test:memory`（渠道契约用例会检查新条目有没有声明能力位与字段）。

界面、数据库、分流规则、MCP 工具都不用改。

## 8. 打开以后，超级智能体怎么知道

渠道开关不是只给界面看的。用户拨开的那一刻起，超级智能体每一轮的提示词里
就多一块 `### 消息接入（实时）`，由 `electron/intake/brief.js` 直接从三张收件箱表生成：

```
### 消息接入（实时）
- 已接 1 条渠道：企业微信（运行中 1）
- 外面有 1 条在等你：张经理 小王，明天下午三点前把方案整理一份发我
- 今日 1 条（提醒 1 · 观察 0 · 知识 0 · 归档 0）
- 取全文：memory_inbox action=recent route=alert；哪个群最热：action=threads
```

四条规矩：

1. **没开渠道就一个字都不写**。空着不占位，不为「未开启」付每轮成本。
2. **上限 240 字**，最多带两条 alert 的一句话。原文永远不进这里。
3. **起不来的要说**。`启动失败 / 配置不全 / 已停止` 会单独一行点名——
   用户问「怎么没收到」时，AI 得先看得到这个，而不是回答「我没收到消息」。
   `待启动` 不算故障（被动渠道刚存下来就是它）。
4. **同一段文本两个出口**：常驻上下文与 `memory_inbox action=brief` 返回的是
   同一份内容，不从两处各写一遍。

配套的三处接线：

| 位置 | 作用 |
| --- | --- |
| `memory/hard-context.js` | `promptText()` 里排在安全状态之前，独立计量，不占四块 3600 字预算 |
| `memory_inbox` 工具 | 新增 `brief`（同款摘要）与 `channels`（开了哪几条、什么状态） |
| 主进程 `astral:intake:new` | 新消息落库即推给窗口，渲染层 1.5 秒节流后重取上下文 |

**为什么要有推送**：只在启动时取一次的话，用户开着窗口聊天，外面来了消息，
提示词里还是旧的——那不叫「知道打开了」。渠道开关拨动、配置保存、渠道移除，
也都会触发同一次刷新（`astral:memory-context-refresh`）。
