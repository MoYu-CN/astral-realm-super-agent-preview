## 0. 问题定义

### 0.1 现状：文件太多、索引太多

| 规划书章节 | 载体 | 内容 | AI 取用方式 |
| --- | --- | --- | --- |
| `3.7` | 项目专属记忆文件（每项目一份，三块） | 简介 / 开发进度 / 任务开发记录 | 先定位项目 → 打开文件 → 找对应块 |
| `3.7` | 项目总文档（全局唯一） | 所有项目 + 逐行事件索引 | 先读总文档 → 拿编号 → 再回查项目文件 |
| `3.5.1` | 派发日记（每天一份） | 顶部浓缩区 + 正文 | 按日期逐份读，周/月摘要再逐层读 |
| `4.3.1` | 主动性行为日记 | 行为统计 + 「是否」信号 | 单独读 |
| `3.8` | 事件记录（外挂记忆库） | 提出时间 + 结果 | 单独读 |
| `3.2` | 知识库（纯工具） | 领域 × 类型的纯知识 | 执行层单独检索 |
| `3.7` | 事件编号表（动态自维护） | 前缀 → 系列 | 每次记录前对照一遍 |

### 0.2 由此产生的问题

- **轮次膨胀**：一次「查某项目最近发生了什么」要跨总文档 → 编号 → 项目文件 → 第 3 块，至少 3–4 轮；写入一次事件要连带改 3–4 个文件。轮次越多，上下文越脏、延迟越高、越容易半途失败。
- **一致性靠人肉维护**：总文档索引、项目文件第 3 块、编号表、派发日记是同一件事的多份副本，任一份漏写就永久不一致（规划书 `3.5.1` 已指出「顶部浓缩区写漏的东西，周摘要不会补回来」）。
- **并发写冲突**：超级智能体与执行层模型同写一个文件，现在只有 `tmp + rename` 原子写，没有事务。
- **崩溃恢复弱**：JSON/JSONL 只能靠 `runs.js` 那类「上限 + 标记 interrupted」兜底，做不到写入幂等与回滚。

### 0.3 目标与验收指标

| 指标 | 目标 |
| --- | --- |
| 单次动作的工具调用轮次 | **1 次**（一次调用完成一个完整动作，含编号分配、索引更新、状态联动） |
| 上下文组装 | 一次 `memory_get_context` 拿齐当前所需，**不默认加载项目正文** |
| 写入一致性 | 一次事务内完成主表 + 索引 + 编号 + 留痕，要么全成功要么全回滚 |
| 真相源 | 数据库为**活跃真相源**；旧文件**封存、永久保留、只读**，可按需回查 |
| 服务形态 | 内置于应用，但**可独立启动**、**可单独打开 / 关闭**；关闭不影响应用其余功能 |
| 知识隔离 | 知识表与项目表**无外键、无引用、不互相索引**（规划书 G7） |
| 回归 | `npm test` 全绿，`npm run doctor` 通过 |

### 0.4 非目标（本阶段不做）

- 不改动规划书中未定的需求（T4、E3/E4/E7、日记压缩规则、G8–G12）；
- 不实现主动性判定、安全沙箱、云端同步、多用户；
- 不重写现有 `config/*.json` 配置体系。

## 2. 方案总览

```text
应用开关  config/settings.json → memory.enabled
  ├─ 开  → 拉起记忆服务（随应用启动）
  ├─ 关  → 不拉起；数据库与封存文件保持不动，应用其余功能不受影响
  └─ 另外：npm run memory 可在主应用未运行时独立启动服务

AI / 智能体（或外部 MCP 客户端）
  │  一次调用（memory_query / memory_write / memory_get_context）
  ▼
记忆服务   electron/memory/server.js   独立进程 · stdio MCP · 自带工具声明
  │  tool-gateway 权限校验 + 审计（经主应用调用时）
  ▼
Store 层   electron/memory/*   事务 · 规则 · 编号 · 压缩 · 封存回查
  ├─ config/memory/memory.db     活跃真相源
  └─ config/archive/**           封存文件（只读、永久、按需回查）
```

要点：

- **内置但可独立启停**：服务随应用发布，不需要外部数据库服务器；可随应用启动、也可 `npm run memory` 单独启动；开关独立控制启停，关闭时数据库文件与封存文件都不动。
- **一个库**：所有活跃记忆数据进同一 SQLite 文件；知识库物理上可放同库，但业务上仍是独立表、不与项目表发生任何关联。
- **访问按角色分区**：知识表只由执行层智能体访问，其余数据只有超级智能体能访问，两者不交叉，因此不存在同时写同一份数据的冲突；外部 MCP 客户端**保留直连**（见 `3.4`）。
- **少量聚合工具**：工具数控制在 **5 个以内**，一次调用在事务内完成「写事件 + 更新索引 + 分配编号 + 留痕」。
- **旧文件封存，不删除**：迁移是**复制进库**，不是搬走；原文件永久保留、只读封存，调用机会少但随时能回查（`memory_query` 的 `source: "archive"`）。
- **索引不再是文件**：查询条件落在表索引上；封存文件用清单表定位，不再「读索引文件 → 再读正文」。

## 3. 数据模型

### 3.1 表清单

| 表 | 承载 | 主要字段 |
| --- | --- | --- |
| `projects` | 项目主体（替代总文档 + 项目文件第 1 块） | `id`, `name`, `folder_path`, `created_at`, `status`, `summary`, `progress`, `main_agent_id` |
| `events` | 事件 / 任务开发记录（`3.7` 第 3 块 + `3.8`） | `id`, `project_id`, `prefix`, `seq`, `started_at`, `ended_at`, `result`, `actor`, `summary`, `merged_into` |
| `proposals` | 提议与结果（`3.8` 外挂事件记录） | `id`, `project_id`, `raised_at`, `result`(接受/拒绝/已下发任务) |
| `dispatch_log` | 派发日记顶部浓缩区（`3.5.1`） | `id`, `project_id`, `occurred_at`, `task`, `to_team` |
| `behavior_log` | 主动性行为日记（`4.3.1`） | `id`, `occurred_at`, `kind`, `signal`(是/否), `count` |
| `knowledge` | 纯知识条目（`3.2`，**无 `project_id`**） | `id`, `domain`, `kind`, `body`, `applies_when`, `status` |
| `event_prefixes` | 动态编号表（`3.7`） | `prefix`, `series`, `created_at`, `owner` |
| `diary_digest` | 日 / 周 / 月摘要（`3.5.1`，规则待定先建表） | `id`, `level`, `period`, `body`, `source_from`, `source_to` |
| `archive_manifest` | 封存文件清单（D3 已确认） | `id`, `path`, `kind`, `period`, `archived_at`, `project_hint` |

### 3.2 索引与约束

| 约束 | 说明 |
| --- | --- |
| `events(project_id, started_at)` | 按项目 + 时间取最近事件，替代逐份读日记 |
| `events(prefix, seq)` 唯一 | 编号不冲突；序号作用域（全局 / 项目内）待确认，见 D7 |
| `knowledge` **不建 `project_id`** | 硬约束：知识库与项目文件无任何关联（G7），从 schema 层杜绝误连 |
| `proposals.result` 枚举 | 只允许 `接受 / 拒绝 / 已下发任务` |
| `dispatch_log` 只存派发四字段 | 不写任务内容、计划书、执行细节（C10） |
| 所有写入走事务 | 一次 `memory_write` 内的多表联动要么全成功要么回滚 |
| 封存只读 | `archive_manifest` 只记录文件位置与元数据，封存文件不回写、不删除 |
| 封存与知识库无关联 | `project_hint` 仅用于文件定位，不建到 `knowledge` 的任何引用 |

### 3.3 规划书规则 → 数据库落点

| 规则 | 落点 |
| --- | --- |
| T1 / T2 开始时间 / 结束时间；未做完结束为空；按项目组织 | `events.started_at` / `ended_at`（可空）、`projects` 粒度 |
| T3 同类事件合并衰减 | `events.merged_into` 指向保留记录，重复时间点存 `event_occurrences` 或摘要字段 |
| T5 用户改主意后旧决定保留 | 只追加、不覆盖；`events` / `proposals` 不物理删除历史决定 |
| T6 时区 / 离线自行纠正 | 存 UTC + 原时区字段，换算由 store 层统一做 |
| E1 事件 = 操作；丢弃的不进记忆 | 只有转成操作的输入才写 `events` |
| E6 只有主智能体上报 | `events.actor` 校验 + `projects.main_agent_id`；工具层拒绝非主智能体写入 |
| C10 只写派发日记 | `dispatch_log` 独立表，不写执行细节 |
| C11 两层拒绝 | 任务内容不落库；`behavior_log.signal` 只记「是/否」 |
| C3 知识只留本质做法、过期即删 | `knowledge` 字段只留 `body` / `applies_when` / `status`；无来源、无验证证据列 |
| G7 知识库与项目无关联 | `knowledge` 无项目外键、无引用表 |
| G4 上下文跟随用户状态、用完即清 | `memory_get_context` 返回临时上下文包，**不落库** |
| 3.8 事件记录独立 | `proposals` + `events` 独立表，不挂到 `projects.notes` 之类的字段上 |

### 3.4 访问权限矩阵（2026-11-09 已确认）

| 数据区域 | 允许访问者 | 入口 |
| --- | --- | --- |
| `knowledge` 表 | 执行层智能体（下级团队） | `knowledge` 工具 |
| 其余全部表（`projects` / `events` / `proposals` / `dispatch_log` / `behavior_log` / `event_prefixes` / `diary_digest` / `archive_manifest`） | **仅超级智能体** | `memory_*` 工具、封存回查 |
| 外部 MCP 客户端 | **保留直连**（范围见 D16） | 直连独立服务 |

- 两类访问者落在不同数据区域，**不会同时写同一份数据**，因此不需要单写者约定或双写锁；
- 数据库仍启用 WAL 作为 SQLite 常规设置，这只是工程兜底，不代表存在并发双写；
- 工具层必须强制分区：`memory_*` 校验调用者为超级智能体，非超级智能体直接拒绝；`knowledge` 工具不提供跨表查询能力。

## 4. MCP 工具设计（核心：减少轮次）

### 4.1 设计原则

1. **聚合入口，不按表拆工具**：一个 `memory_write` 带 `action`，而不是每表一个工具。
2. **事务内联动**：分配编号、对照前缀表、更新项目状态、写留痕，同一次调用内完成。
3. **查询一次给全**：`memory_query` 直接返回所需字段，不再返回「编号，请再去查详情」。
4. **工具总数 ≤ 5**，避免 AI 在工具选择上再多一轮。
5. **按角色分区**：知识读写与其余记忆数据由不同角色访问，工具入口就要拦住越权调用（见 `3.4`）。

### 4.2 工具清单

| 工具 | 动作 | 一次调用替代了什么 |
| --- | --- | --- |
| `memory_query` | 按 `project / time_range / prefix / status / keyword / include` 一次查回事件、提议、派发记录；`source`: `live`（默认）/ `archive`（封存回查） | 读总文档 → 找编号 → 打开项目文件 → 读第 3 块（3–4 轮）；封存回查也走同一入口，不新增工具 |
| `memory_write` | `action`: `event / proposal / dispatch / behavior / project`；内部事务完成编号分配、前缀对照、项目状态、留痕 | 写事件 → 改索引 → 改项目文件 → 写日记（4 轮） |
| `memory_get_context` | 按当前用户状态返回工作上下文包（G4），用完即清，不落库 | 读总文档 → 简介 → 进度 → 派发日记 → 事件索引（5 轮） |
| `knowledge` | `action`: `upsert / query / expire`；纯知识读写，与项目表无关联 | 执行层单独检索知识库 |
| `memory_compress` | `level`: `day / week / month`；**压缩规则未定，先保留接口不实现** | 未来替代手工压缩 |

权限映射（按 `3.4` 分区）：`memory_*` → capability `memory` **且仅超级智能体可调用**；`knowledge` → `knowledge.read` / `knowledge.write`，开放给执行层智能体（`tool-gateway.js` 现有项）。外部 MCP 客户端直连保留，权限范围见 D16。

### 4.3 参数示例

`memory_query` 入参示例：

```json
{
  "project": "投票项目",
  "time_range": { "from": "2026-11-01", "to": "2026-11-09" },
  "prefix": "BB",
  "include": ["events", "proposals", "dispatch"],
  "source": "live",
  "limit": 20
}
```

`memory_write` 入参示例：

```json
{
  "action": "event",
  "project": "投票项目",
  "prefix": "BB",
  "started_at": "2026-11-09T14:20:00+08:00",
  "ended_at": null,
  "result": "已下发任务",
  "summary": "修复 bug",
  "actor": "主智能体"
}
```

返回统一结构：`{ ok, data, count, truncated }`，`truncated` 用于提示上下文裁剪，不静默丢数据。

`source: "archive"` 时走封存文件：先按 `archive_manifest` 定位文件，再只读返回内容；默认 `live` 不碰封存文件，因此「调用机会少」不会拖慢常规查询。

### 4.4 轮次对比（量化目标）

| 场景 | 现状（文件 + 索引） | 本方案 | 轮次 |
| --- | --- | --- | --- |
| 查某项目最近事件详情 | 总文档 → 编号 → 项目文件 → 第 3 块 | `memory_query` | 3–4 → **1** |
| 记录一次询问 + 确认 + 下发 | 事件记录 → 总文档索引 → 项目文件 → 派发日记 | `memory_write` | 4 → **1** |
| 为新任务组装上下文 | 总文档 → 简介 → 进度 → 派发日记 → 事件索引 | `memory_get_context` | 5 → **1** |
| 合计 | 12–13 轮 | 3 轮 | **约 4×** |

## 5. 接入点（具体到文件）

| 文件 | 改动 | 说明 |
| --- | --- | --- |
| `electron/memory/server.js`（新） | 独立进程入口：stdio MCP server、工具声明、启停与信号处理 | `npm run memory` 可直接跑；不经 HTTP 桥，自己读写库文件 |
| `electron/memory/db.js`（新） | 建库、schema、索引、版本迁移、WAL | CommonJS 工厂 `createDb({ configDir })` |

## 13. 文本文件 vs 数据库：步骤成本分析（2026-11-09）

### 13.1 三个方案的轮次

| 方案 | 查一件事要几轮 | 谁维护索引 | 写入要改几处 |

| --- | --- | --- | --- |
| 手写文本文件（原规划书的分层） | **12–13 轮** | 人 / 智能体逐层维护 | ≥ 4 处（编号表、总文档、项目文件、派发日记） |
| 数据库 + 聚合工具（第 4.4 节） | **3 轮** | 数据库 | 1 次事务 |
| 本轮 `/api/record` 一次聚合 | **1 轮** | 数据库 | —（只读预览） |

### 13.2 手写文本文件的完整步骤

```text
① 定位项目文件夹
② 打开项目总文档 → 找到项目与事件编号
③ 按编号打开项目专属记忆文件 → 翻到第 3 块任务开发记录
④ 查事件编号表 → 解析 BB001 / P001 的含义
⑤ 打开派发日记 → 先读顶部浓缩区、再翻正文
⑥ 人工把几处时间线合并成一条
⑦ 想看旧文件 → 查封存清单 → 打开封存文件 → 摘出内容
⑧ 把内容整理成可喂给 AI 的上下文
⑨ 写入时同步改：编号表 + 总文档 + 项目文件 + 派发日记
```

问题不在「文件不好」，而在**每层索引都要靠一次额外的打开动作去解析**，且正文是自由文本，条件过滤只能靠通读。

### 13.3 本质区别

| 维度 | 文本文件 | 数据库 |

| --- | --- | --- |
| 索引 | 另写一份索引文件，改动要手工同步 | 表索引由数据库维护，写入即生效 |
| 定位 | 读索引 → 拼路径 → 开文件 → 在正文里找 | `WHERE project / time / prefix` 直接返回结构化行 |
| 一致性 | 多处文件分别写，漏一处就对不上 | 一次事务：编号分配、前缀登记、事件落库、留痕要么全成功要么回滚 |
| 关联 | 靠编号字符串人工对应 | 服务端按 `project_id` 一次查回事件 / 提议 / 派发 |
| 正文 | 整篇读，长文本难截取、难预览 | 字段化 + `/api/record` 一次返回全文与渲染结果 |
| 封存 | 找到路径再打开文件 | 清单表定位，只读回查走同一入口 |
| 给 AI 用 | 人先把内容拼成上下文 | 服务端直接产出上下文包，复制即用 |

### 13.4 本轮实际减少的步骤

- 新增 `GET /api/record?name=&id=`：把「查表 → 找正文 → 查关联 → 查封存 → 拼上下文」压成**一次 GET**；响应里 `row` / `content` / `related` / `archive` / `bundle` 一次给全。
- 用户侧从「打开编辑器 → 找文件 → 翻到对应段落」变成**点一行 → 看全文 → 复制上下文包**（1 次点击 + 1 次复制，不需要打开文件系统）。
- 全局搜索结果直接带 `id`，点结果即预览，省掉「再搜一次表定位」这一轮。
- 封存原文并入同一个响应，回查旧文件不再单独开一轮。

### 13.5 还能再省（P1，已于 2026-11-09 落地，见第 14 节）

- 把这份聚合结果注册成 MCP 工具 **`memory_get_record`**，让智能体侧也只需一次调用，不必自己拼上下文包；
- 写侧同理：把「先查编号表 → 再决定前缀 → 再写事件」保持在 `memory_write` 单事务内（已实现，不增加工具数）；
- 若把 `/api/record` 的结果直接作为 `memory_get_context` 的一部分返回，AI 侧「查 + 组装」可合并为 1 轮。

### 13.6 边界

- 数据库是**活跃真相源**，但旧文件按 D3 **封存、永久保留、只读**；「少步骤」不等于「删文件」，需要时仍可回查。

- 控制台全部只读，视图层不写库；日 / 周 / 月压缩规则未定（D5），`memory_compress` 仍只留接口。

- 以上轮次按第 4.4 节的三个典型场景估算，用于说明「索引层级 → 调用轮次」的关系，不是性能基准。

## 15. 硬性上下文与星图（2026-11-09）

> 用户两条要求：① 超级智能体的硬性上下文界面要能查看、能编辑；② 用更清楚的形式展示记忆文件之间的联系，加一个星图页面。

### 15.1 硬性上下文

**定位**：每一轮都进入超级智能体系统提示词的一小块固定内容，有字数硬上限；与按需检索的项目记忆、事件记录分开。

**存储**：

| 项 | 实现 |
| --- | --- |
| 表 | `hard_context`（`slot` 主键 / `body` / `updated_at` / `revision`） |
| 版本 | `SCHEMA_VERSION` 1 → 2；v1 库打开时补种默认四块 |
| 重种规则 | 只在升级时 `INSERT OR IGNORE`；用户清空后再次打开不会塞回默认内容 |
| 历史 | 只留当前正文 + 修订号，不存历史版本（审计不在本库范围） |

**接口**：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/hard-context` | 四块正文、字数、上限、修订号、写入开关 |
| POST | `/api/hard-context` | 保存单块：`{ slot, body }`，需 `application/json` |

**取用**：`memory_context` 的返回里新增 `hardContext.blocks / total / budget / text`；硬性上下文常驻，不参与「用完即清」。

**界面**：

- 「硬性上下文」页：左侧四块卡片（字数条 / 未保存标记），右侧「编辑 / 查看」双模式；
- 编辑区是等宽 textarea，显示 `当前字数 / 单块上限`、保存 / 还原、`● 未保存`；
- 底部长条按块着色显示 3600 字预算，并列出注入顺序：身份与边界 → 硬性规则 → 用户长期画像 → 默认授权 → 系统提示词；
- 主界面「上下文」面板新增「硬性上下文」入口，直达控制台 `#hard`；不在主面板直接编辑，避免与项目上下文混成一份。

### 15.2 星图

**两种模式**：

| 模式 | 数据 | 用途 |
| --- | --- | --- |
| 文件关系 | 前端固定的概念节点 + 实时计数 | 看清项目总文档 / 项目专属记忆文件 / 三块 / 日记 / 事件记录 / 知识库之间的关系 |
| 数据星图 | `GET /api/starmap` 返回的真实节点与边 | 项目为星、事件为卫星；知识库是独立岛 |

**接口**：`GET /api/starmap` 返回 `nodes` / `edges` / `stats`：

- 节点：`super` / `hard` / `master` / `diary` / `events` / `archive` / `behavior` / `proposals` / `knowledge`，以及项目、项目下最近 10 个事件、最近 16 条知识；
- 边：超级智能体 → 硬性上下文 / 项目总文档 / 派发日记 / 事件记录 / 提议 / 行为日记；项目总文档 → 项目；项目 → 事件；项目总文档 → 封存清单；
- **知识库节点 `isolated: true`，不与任何节点连边**（G7）；知识条目只围绕知识库原子排布，不连出岛外；
- 超过 6 个项目、7 个事件/项目时只画最近部分，`truncated` 标记并在页脚提示。

**前端（三维）**：`view/starmap3d.js`，纯 Canvas 2D 手写透视投影，零外部依赖。

- **投影**：世界坐标 → 绕 Y 轴偏航 → 绕 X 轴俯仰 → 沿 Z 平移相机距离 → 透视除法（`s = focal / zc`）。近大远小、近亮远暗，另有一层固定在天球上的尘点提供旋转视差。

- **三维布局**：超级智能体在原点；治理层（硬性上下文 / 总览 / 提议 / 行为）在上方；项目体系（总文档 / 专属文件 / 三块）在 +X；记录体系（派发日记 / 事件 / 封存 / 前缀）在 -X；知识岛孤立在远端。数据星图里项目均匀落在三维圆环上、事件按球面黄金角绕项目成团，知识条目绕知识岛。
- **取景**：全景机位不写死，按当前图自动算——先取节点重心做目标点，再交替做「缩放到画布 86% × 84%」与「平移到画面中心」共 10 轮。包围盒把星体半径与标签宽度都算进去，换图不用手调坐标。
- **交互**：拖拽旋转（俯仰夹 ±68°）、滚轮推拉、点击星体后相机在 720ms 内飞到它的三维坐标并居中（星体落在画面正中，实测偏移 0.0 px），「总览」在 780ms 内退回全景。聚焦期间工具栏显示「聚焦 · 名字」并点亮「总览」，切模式或点总览会顺手收起档案卡。
- **标签**：13px 主标签 + 10px 次标签，先描深色边再填字；位置冲突时先试星体下方，仍冲突才隐藏——保证任一时刻标签不互相压字。
- 数据星图点击项目 / 事件 → 复用右侧 dock 预览完整记录；文件关系点击节点 → 打开「文件档案」卡（职责 / 关系 / 规则 / 跳转按钮）。
- 概念图只画已确认关系；`3.8` 的「事件记录 vs 任务开发记录是否同一份」不画线，写进「任务开发记录」的文件档案，避免把待确认项画成事实。

三维化过程中踩到三个坑，都已处理并写进探针：

1. **取景要算星体半径和标签宽度**。只按节点中心算包围盒的话，边缘那颗的知识库会被裁掉半颗、标签出画。另外透视下包围盒中心不等于画面中心，只缩放不平移会整体偏上，必须「缩放 + 平移」交替迭代。
2. **隐藏视图里画布是 0×0**。从总览点进星图时，`#view-starmap` 还是 `display:none`，`getBoundingClientRect()` 返回 0，按 1×1 算出的全景机会偏到天外。现由 `needHome` 标记：等画布拿到真实尺寸再落位一次，之后不再干预用户自己的视角。
3. **隐藏窗口里 `requestAnimationFrame` 会被节流**，补间根本不推进（表现为相机状态变了、画面没动）。自检窗口必须 `show: true` + `backgroundThrottling: false`，否则测出来的是「没动画」。

上一版 2D SVG 的两个坑一并记录，避免以后回头改成 SVG 时重犯：坐标换算要扣掉 `preserveAspectRatio="meet"` 的留边；画布级监听只能绑一次（`renderStarMap` 只换子节点、svg 本体常驻，绑定叠两层会让滚轮倍率按次方放大）。

## 16. 显示上限 · 上下文控制 · 身份边界 · 直连会话（2026-11-09，十二轮）

这一轮回答四个问题：星图画多了会不会卡、上下文到底能不能控、非管理员能做什么、超级智能体有没有自己的门口。四项都在主进程落了硬边界，不是界面上的隐藏。

### 16.1 星图显示上限

数据量增长后三维星图的绘制开销按节点数线性上升，且标签避让是 O(n²) 的。现在的做法是**服务端取数时就截断**，前端不拿到超出部分，从源头控制节点总数。

**上限表**（`electron/memory/view-server.js` 的 `MAP_LIMITS`）：

| 项 | 上限 | 说明 |
| --- | --- | --- |
| 项目 | 6 | 按「最近有事件的」排序取前 6，不是按创建时间 |
| 每项目事件 | 6 | 卫星只挂最近的，久的留在记录里可查 |
| 无项目事件 | 6 | 未归属项目的事件单独一组 |
| 知识条目 | 12 | 知识岛上的原子 |
| 节点总数 | 220 | 兜底，超出时先砍事件、再砍知识条目，并同步清理悬挂边 |

**截断报告**：`GET /api/starmap` 除 `nodes` / `edges` / `stats` 外，新增三个字段——

- `limits`：上面这张表，前端直接用，不再各写一份常量；
- `shown`：实际画出来的 `projects` / `events` / `looseEvents` / `knowledge`；
- `truncation`：分项布尔 + `any` 汇总，用于页脚提示。

`stats.projects` / `stats.events` 报的是**总量**而非显示量，页脚因此写成「总量（显示 N）· 显示上限 6 项目 / 每项目 6 事件 / 12 知识」，用户能看到自己被截掉了多少。

**兜底裁剪顺序**是刻意的：事件是卫星、视觉密度最高，先砍它；知识条目次之；项目与治理层节点（超级智能体 / 硬性上下文 / 总览 / 日记 / 事件记录 / 提议 / 行为）永不裁剪——它们是骨架，缺一颗整个图就读不懂了。

### 16.2 上下文可控性

原来的提示词是一整段拼出来的字符串，用户既不知道里面有什么，也没法只关掉其中一部分。现在拆成**层**。

**15 个层，4 个固定、11 个可关**（`app/js/llm.js`）：

| 层 | 归属 | 内容 |
| --- | --- | --- |
| `core` | 固定 | 身份与基本行为准则 |
| `permissions` | 固定 | 权限与只读边界 |
| `tools` | 固定 | 可用工具与调用约定 |
| `output` | 固定 | 输出格式要求 |
| `persona` | 可关 | 角色人设 |
| `identity` | 可关 | 名字 / 简称 / 头像相关自称 |
| `project` | 可关 | 项目上下文（`globalNotes`） |
| `profile` | 可关 | 用户画像 |
| `hard` | 可关 | 硬性上下文的四块（仅在 `opts.hard === true` 时注入，避免与身份层冲突） |
| `bio` | 可关 | 该成员的专属上下文（`agent.context.notes`） |
| `skills` | 可关 | 技能规范 |
| `notes` | 可关 | 项目提醒 |
| `protocol` | 可关 | 协作协议（派单 / 交付格式） |
| `data` | 可关 | 星界数据快照（项目 / 任务 / 知识计数） |
| `thinking` | 可关 | 思考与自检要求 |

**单一来源**：`promptSections(agent, opts)` 返回 `[{ key, label, text, fixed }]`，`buildSystemPrompt` 只是把它过滤后拼接。控制台的字数统计、开关状态、「查看完整提示词」弹窗全部读同一个函数，因此**面板上显示的字数就是实际发出去的字数**，不存在两套算法对不上的情况。

**开关落盘**：`settings.context.layers[key] !== false`，只有显式关掉才算关，默认全开。固定层无视开关，`contextLayerOn` 直接返回真——这样即使用户把 settings 改成全 false，也不会把模型变成没有身份和权限约束的裸壳。

**在哪控制**：dock 的「上下文注入控制」区块。团队模式取选中成员、单飞模式取当前助手，逐行显示层名、固定/超级智能体标签、实时字数与开关；改动即 emit `dock:refresh` 重算，不重启。字数实测：默认 968 字，其中硬性上下文 799 字；关掉「技能规范」后 984 → 683（Δ301）。

### 16.3 身份与安全边界

三档身份，能力驱动。**身份唯一来源是 `settings.json → profile.role`**，不是界面状态、不是本地存储。

| 身份 | 等级 | 能做什么 |
| --- | --- | --- |
| 管理员 `admin` | 3 | 全部：设置、供应商、编制、插件、记忆写入、身份管理 |
| 成员 `member` | 2 | 对话、工具、写文件、管项目与长任务、读记忆、看只读控制台 |
| 游客 `guest` | 1 | 只读浏览：不能发起模型调用、不能写任何文件、不能读记忆 |

**15 项 capability**（`ROLE_CAPS`）：`chat` / `tools` / `files.write` / `project.manage` / `job.manage` / `knowledge.write` / `memory.read` / `memory.console` / `memory.write` / `settings` / `providers` / `roster` / `plugins.manage` / `role.manage`，以及身份本身。每条 IPC 进主进程第一件事就是 `roleCan(cap)`，不通过直接 `deny(cap)` 抛错。

**为什么必须在主进程判**：渲染层隐藏按钮只是不显示，DevTools 里一行 `window.astral.saveConfig(...)` 就能绕过。所以 `saveConfig`、`providerKey:set`、`skills:upload`、`mcp:call`、`knowledge:save`、`jobs:create`、`writeProjectFile`、`session:save`、`runs:start`、`llm:start`、`memory:prompt`、`memory:openConsole` 全部逐条复核。游客写 `settings.json` 和会话文件的路径单独堵死——那是最容易被用来提权的两个入口。

**防自我提权**：非管理员保存 settings 时走 `sanitizeSettingsForRole`，`permissions` / `agentDefaults` / `superAgent` / `memory` / `bridge` / `triggers` / `plugins` / `retry` / `speech` 九段被锁定为磁盘现值，`profile.role` 强制保持磁盘值，`profile.rolePin` 与 `hasPin` 直接剥离。也就是说成员即使手改请求体，也改不动自己的身份和权限。

**切换身份要口令**：`profile.rolePin` 存的是 SHA-256，只留主进程，**永不随 `bootPayload` 下发**，渲染层只拿到 `hasPin` 布尔。规则是——

- 管理员 → 成员 / 游客：必须已经设过口令（防止把自己锁在门外）；
- 成员 / 游客 → 管理员：必须验对口令；
- 非管理员发起切换：直接拒（「只有管理员可以切换其他身份」）。

**控制台写权限**：`openMemoryConsole` 按 `memory.write` 传 `write` 给子进程，环境变量 `MEMORY_VIEW_WRITE=0/1`。成员打开的是只读控制台，`POST` 一律 403。切换身份时如果写权限变了，会先 `stopConsole()` 再重启——否则端口被旧进程占着，`portOpen()` 会直接复用，管理员写完再切成员仍带着写接口。

**界面**：品牌区右侧的身份徽标（管理员 / 成员 / 游客，三色），点击进「设置 → 个人资料」。设置页按角色过滤——非管理员只见 `profile` / `appearance` / `about`，身份卡与能力矩阵也只有管理员能看。游客的输入框是 `disabled` 的，占位提示写「游客为只读身份 · 请到「设置 → 个人资料」切换为管理员或成员」。

### 16.4 超级智能体的直连会话

超级智能体原来只在编排链路里被动出现，用户没有直接跟它说话的地方。第一版做成了独立窗口（三标签弹层），但那个形态是错的：**它把一个会话做成了应用窗口**。用户的原话是「跟普通的对话一样，只不过在左边的对话栏里面是独立显示」，所以现在改成——

**它是一条会话，不是一扇窗。**

| 维度 | 做法 |
| --- | --- |
| 入口 | 左侧栏独立一条（`.rail-super`），和项目、成员并列，点一下就进 |
| 主区 | 复用同一个 `#stream`、同一套消息节点、同一个输入框；没有第二个 DOM 树 |
| 顶栏 | 标题换成它的名字，副标题写「直连会话 · 不经过派单 · 模型 · 上下文隔离」，右侧按钮变「资料」 |
| 视图切换 | 隐藏——直连只有一条线，`AI ↔ AI` 在这里没有意义 |
| 右栏 | 进来自动收起；点开只剩「插件」，任务 / 上下文 / 知识库都不出现 |
| 离开 | 点任意项目或成员即回到项目会话；新建对话、革新同样先离开 |

**怎么做到「复用同一套渲染」**：消息不塞进 `state.messages`（那是项目会话），而是放 `state.superChat.messages`，再让 `viewMessages()` 在直连模式下返回它。这样 `renderThread` / `createNode` / `renderBody` 一行都不用改，流式、Markdown、折叠、消息头全部自动一致。`findMsg(id)` 同时查两个数组，渲染层不需要知道自己在哪条线上。

**消息形态**：`{ kind:'user'|'agent', channel:'user', thread:'super', agentId:'super', name, short, color, glyph, avatar, meta:{ model } }`——和普通成员消息同构，只是 `agentId` 不指向编制里的任何人（`head()` 的 `live` 查不到就退回消息自身的字段）。

**持久化**：`config/super-agent/session.json`，独立 IPC（`astral:superSession:load|save`），写操作要 `chat` 能力。切项目不会带走它，也不进项目历史。

**模型解析**：`resolveAgent()` 的每个候选供应商都要在供应商表里核对一次。原来的写法直接采信编制里记的 `providerId`，供应商被删掉之后就会出现「有供应商、却报未配置模型」。

**右栏**：直连会话不挂项目面板。进去时右栏自动收起；点开只剩「插件」一页，任务、上下文、知识库全部隐藏。规则集中在 `syncModeTabs()` 一处判断，`SUPER_DOCK_PANES` 只放行 `plugins`；`openDockPane()` 与 `render()` 用同一份规则兜底，避免别处直接调用时把面板又拉出来。离开时按进去前的页签与展开状态还原（用户在直连里自己点开过就不替他收起）。

**任务去哪看**：任务文件夹、长任务、本轮进度属于项目，不属于这条会话，所以回项目会话的「任务」页看——那页顶上多一行「任务文件夹 + 在文件夹中打开」，其余照旧。「看见它在干什么」的要求还在，但不会在直连会话里堆一屏跟对话无关的东西。

**资料**——头像（`pickAvatar(128)`）、名字、简称、简介、供应商、模型，走普通单页表单弹窗（`openModal`，无标签栏），改完写 `settings.superAgent` 并 emit `super:changed`，侧栏名称、消息头、空态同步变。「编辑硬性上下文」直达控制台的 `hard` 视图。

**边界**：它是**会话，不是第二个编排入口**。不派单、不建项目、不改团队，只说话和看进度；要它动手仍然走项目会话的编排链路。这样「能随时说话」不会变成绕过审批的第二条后门。游客能点开，但输入框禁用、空态写明原因。

## 17. 项目权重网与按权重回忆（2026-11-10，十三轮）

### 17.1 为什么要这张网

原来的 `memory_context` 是「最近 20 条事件，全项目」。三个问题：

- 项目一多，无关事件占掉大部分字数；
- 模型分不清哪条和当前问题有关，只能全信或全不信；
- 每次回忆的成本随库增长线性上升。

改成先回答一个更小的问题：**这次该回忆哪几个项目？** 项目层选对了，事件层的候选只剩几十条，再精排一次就够。这就是「权重网」的位置——它不是展示用的关系图，是检索的前置路由。

### 17.2 网长什么样

三张表，都是可重算的派生数据：

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `project_terms` | 每个项目的词向量 | `project_id` / `term` / `weight`（已归一化 tf-idf） |
| `project_links` | 项目两两之间的近似度 | `a` / `b` / `weight` / `lexical` / `cooccur` / `hits` |
| `recall_log` | 每次回忆的流水 | `query` / `projects` / `chars` |

三条约定：

1. **节点不是新建的**：`projects` 表本身就是节点。记忆库一贯用项目名当自然键，事件里的 `project_id` 记的也是名字，所以镜像项目时直接用名字当 id，历史事件才对得上。
2. **边是无向的**：写入时按字典序归一成 `(a, b)`。不归一的话 `(甲,乙)` 和 `(乙,甲)` 会各存一行，共现计数写进反向那行，看起来就像「权重没涨」。
3. **`hits` 是唯一跨重建保留的字段**：它记的是「这两个项目一起被回忆过几次」。`lexical` 每次重建都会重算，`hits` 不会——这是网唯一会学习的地方。

### 17.3 打分怎么算

1. **分词**：中文按二元组切（`投票项目` → 投票 / 票项 / 项目 / 投票项目），英文与数字按词切，虚词丢掉。不引分词库：装一个词典只为切项目名，代价大于收益。
2. **项目档案**：名字 + 摘要 + 进度 + 最近 20 条事件摘要。只用最近 20 条是刻意的——更早的事已经被后来的覆盖，全量只会把噪音带进向量。
3. **tf-idf**：语料内 idf，向量归一化，点积即余弦。
4. **名字命中**：整名出现在问题里 +0.5；名字包含问题 +0.35；名字片段命中过半最多 +0.25。片段命中要求过半，否则「默认项目」只重合一个「项目」也会被当成名字命中。
5. **覆盖率门**：只命中「项目」这种公共词时，余弦也能到 0.16。所以要求命中的查询权重 ≥ 30% 才算「内容相关」；名字命中不受这条限制。
6. **图扩散**：一跳，取最强的那条边（不是求和，避免枢纽项目把全网带偏），alpha 0.35。
7. **学出来的关联**：完全没命中的项目，只有在「一起被回忆过 ≥2 次且边权 ≥0.4」时才允许被邻居带进来。一次误召回不该形成联想。

阈值：项目分 ≥ 0.15，默认最多 3 个项目。

### 17.4 回忆返回什么

| 层 | 规则 |
| --- | --- |
| 项目 | 最多 3 个，每个带相关度与理由（按名命中 / 内容相近 / 关联项目） |
| 事件 | 每个项目最多 2 条，全局再取前 6；排序 = 查询匹配 + 近 30 天时间衰减 |
| 知识 | 全局排，阈值 0.06，最多 4 条 |
| 文本 | 按 `budget` 拼接（默认 900 字，范围 200–4000），超了直接截断，不硬塞 |

每次回忆写一行 `recall_log`：查了什么、动了哪几个项目、返回多少字。它不参与打分，只用于回看与调参。

### 17.5 接进星界

- **工具** `memory_recall`：模型自己决定何时调用。描述里写明「回答过去的事之前先调它，不要凭印象编」。
- **IPC**：`astral:memory:recall`（`memory.read`）、`astral:memory:syncProjects`（`chat`）、`astral:memory:net`（`memory.read`）。
- **项目镜像**：`saveProjectsNow()` 与启动各同步一次，权重网节点与左侧项目列表一致；按名字去重，重复同步只更新目录与摘要。
- **提示词**：工具清单里多一句「回忆过去的项目、做过的决定、踩过的坑之前，先用 `memory_recall` 查一次」。只有工具真的在清单里时才加，没装记忆库的部署不会看到这句。
- **控制台**：三张权重表已进中文表清单，可以直接看到词向量、连边与回忆记录。

### 17.6 验收

| 检查 | 结果 |
| --- | --- |
| `npm run test:memory` | **25 项全绿**（新增 5 项：分词与对称性 / 只取相关项目 / 对不上返回空 / 共现加权 / 项目镜像） |
| `npm test` | 28 项全绿 |
| `npm run probe:net` | 全绿（真实 Electron + 真实记忆库） |

实测：三个历史项目 + 镜像节点共 5 个节点、2 条边；查询「投票项目登录报错那次怎么修的」→ 只命中投票项目（相关度 1.00，按名命中），取回 1 条事件，文本 75 字。「默认项目」只共享「项目」一词，被覆盖率门挡在门外——这正是改之前会混进来的那类结果。

### 17.7 待确认

- 要不要接 embedding：中文二元组对「换个说法」无能为力（「登录报错」vs「鉴权失败」），接向量模型能补上，但要付每次建网的调用成本；
- 阈值 0.15 / 覆盖率 0.3 / 扩散 0.35 是拍的，需要真实用一段时间再调；
- 共现只增不减，要不要加时间衰减——半年没一起出现的边慢慢变细；
- 事件层现在按项目取最近 20 条再排，单个项目事件上千后要不要上 FTS5。

## 18. 三张网：项目 / 事件 / 时间（2026-11-10，十四轮）

第 17 节只解决了「该回忆哪几个项目」。这一轮把网拆成三张互不干涉的网，并把相关度真正画到线上、把「这一周 / 周一这个点」记成独立的文档。

### 18.1 一句话边界

| 网 | 回答的问题 | 表 | 是否参与回忆打分 |
| --- | --- | --- | --- |
| 项目网 | 这次该动哪几个项目 | `project_terms` / `project_links` | 是（前置路由） |
| 事件网 | 这两件事说的是不是同一件事 | `event_terms` / `event_links` | 是（只在已命中的项目内精排） |
| 时间网 | 这个时间点通常在做什么 | `week_docs` / `time_slots` | 否，完全独立 |

三张网各建各的索引，互不引用。项目网里不会出现事件 id，事件网里不会出现项目 id，时间网既不读词向量也不写连边，只读事件的时间戳。

### 18.2 事件网

- 节点文本 = 事件系列名 + 前缀 + 事件摘要，**刻意不放项目名**。放了项目名，同一个项目下的事件会先连成一团，事件网就退化成项目分组。
- 仍然用中文二元组 + tf-idf + 余弦，`pairwise` 阈值 0.06；每条事件最多留 4 个最强邻居（`trimLinks`），避免事件一多就连成一张看不清的网。
- 重建时与项目网一样保留 `hits` / `cooccur`；`reinforceEvents` 只加重**已有**连边，不因为「本次一起被回忆出来」就凭空造边。
- `recall` 在已命中的项目内做一次一跳扩散：强事件最多带 2 条关联事件进来，返回里用 `via: 关联事件` 标明来源，文本里加「· 关联」。无关项目仍然一条都不会混进来。

### 18.3 连线上的百分比

- `/api/starmap` 从 `project_links` / `event_links` 各取一批边，只连**已经在图上显示**的星，边上带 `percent` 与 `label`（例如 `75%`）。显示门槛 20%，项目边上限 24 条、事件边上限 40 条。
- 权重边默认不画：星图先讲结构，聚焦或悬停某颗星时，它的相关度边才亮成青色，并在**线上**画出百分比胶囊（`starmap3d.drawEdgeLabels`）。标签压在星体之上、名字之下，中点压到星体上时退到连线 28% 处。
- 聚焦带权重边的星体时，相机会自动退到「最远邻居之外」（`reach + 220`），否则邻居落到相机背后，连线和百分比都画不出来。
- 概念图的关系边（「每轮常驻」「持有索引」）仍不写数字：它们不是权重。
- 主界面「项目设置」（左侧项目条目的 ✎）里也列出前 5 个相关项目与同样的百分比，方便不看星图时也能查；数据来自同一个 `astral:memory:net`，不会算出第二套权重。

### 18.4 时间文档（按周）

- `week_docs` 一周一篇，主键是 ISO 周编号（`2026-W45`）。正文自动汇总：这一周几条记录、几个项目、活跃几天、每个项目最近 4 条事件、最集中的时段。
- 时区按本机时间算：周一为一周之始，ISO 周编号按「这周的周四属于哪一年」定，跨年不会串。
- `source = auto` 的周记每次重建都会刷新；改成 `manual` 的行会被保留，不被覆盖。控制台只读展示，不提供编辑器。
- 控制台「时间」页的右侧按周列出文档，点一周换一篇；左侧是 7 天 × 24 小时的热力图。

### 18.5 时间网与提醒（权重强相关于时间）

**口径先说死：权重的第一维是时段，不是活动。** 它回答的是「到这个点了，用户该干什么、这件事有多确定」，是 `P(活动 | 周几 + 小时)`，不是「这个活动有多重要」。时段是键、是主轴，活动只是它下面的候选；计算过程不读词向量、不看内容相似度、不引用项目网或事件网，只吃事件的时间戳。

- `time_slots` 的主键是 `周几 + 小时 + 当时在做的事`。事情取项目名；没有项目归属的事件退到事件系列名，`kind` 记下是项目还是系列。
- **规律按周算，不按条数算**：同一周、同一时段、同一件事只贡献一份权重。一个晚上连写十条事件，不等于连续十周都在做这件事。衰减单位是周：`weekWeight = 0.5 ^ (隔了几周 / 13)`（13 周 ≈ 91 天半衰期）。
- 三个量分开记、不混为一谈：

  | 字段 | 含义 | 例子（周一 21 点连续 3 周只做「星界」） |
  | --- | --- | --- |
  | `share` | 在**这个时段**的历史里，它占多少 | 100% |
  | `weeks` / `reliability` | 跨了几个不同的周；`reliability = weeks / (weeks + 2)` | 3 周 / 0.6 |
  | `weight` | `share × reliability`，即界面上的**时间置信度** | 60% |

  只出现过 1 周时可靠度 0.33，宁可给低分，也不假装「100% 会做」。这是这一轮修掉的关键偏差：旧版把时段内事件条数当成置信度，三条同一周的事件就会报 100%。

- `memory_time` 的 `suggest` 只在「**至少 3 个不同的周**于同一时段重复、且时间置信 ≥ 40%」时开口（`minWeeks` / `minWeight` 可调），返回提醒与可直接交给模型的 `prompt`；样本不足就明确说没形成跨周规律，不编作息。
- 主界面启动后 2.2 秒问一次，命中时弹一条不打断聊天的提示条：「连续 3 周你都在推进『星界』……要不要我先起个头？」接受只把任务写进输入框，**不会自动发送**；「今天不用」按本地日期记一次，当天不再提醒。
- 控制台「时间」页每格都写清「时段占比 / 跨了几周 / 时间置信」，避免把占比当成时间上的确定性。
- 这条链路只写派生表（`time_slots` / `week_docs`），不改任何事件、项目或会话记录。

### 18.6 接线

| 位置 | 新增 |
| --- | --- |
| 数据库 | `SCHEMA_VERSION 5`：`event_terms` / `event_links` / `week_docs` / `time_slots`（v4 → v5 给时段表补 `share` / `reliability` / `weeks`，纯派生缓存整体重算） |

| 控制台 | `/api/time?week=...`、`/api/starmap` 的权重边、新增「时间」视图 |
| 提示词 | 只有 `memory_time` 真在工具清单里时，才额外写「问作息前先取真实记录，样本不足就直说」 |
| 中文映射 | 四张新表与列名、周几 / 类型 / 来源的枚举翻译 |

### 18.8 边界与下一步

- 相关度仍是**词法**近似：中文二元组对「换个说法」无能为力，`75%` 表示内容重合 + 共现，不表示语义等价。接 embedding 是下一步。
- 时段只用「周几 + 小时」一个维度，没区分工作日 / 假期，也没做跨时区迁移；用户换时区后旧桶会保持原样。
- 周记目前只按最近 12 周（手动 `sync` 可到 52 周）刷新，更早的历史周不会自动补文档。
- 提醒默认门槛是「跨 3 周 + 时间置信 40%」，可靠度用 `weeks/(weeks+2)`；都是拍的，真实用一段时间后按打扰率再调。
- 时段之间没有做邻近扩散（20 点不会借 21 点的权重）：口径是权重强相关于**具体的时段**，把相邻小时混起来反而会稀释这个相关性。

## 19. 进程层：阶段 × 指令类型 × 时段（2026-11-10，十六轮）

第 18 节把时间权重定成 `P(活动 | 周几 + 小时)`。用户随后把口径推进一步：**时间网不止是时钟，还要看用户/项目在时间轴上走到哪一步**——这个阶段常收到什么指令、项目走到什么时候开始需要这类工作，就可以问他；概率由「平时的变化」决定，而不是一次统计定死。

### 19.1 口径

权重是 `P(这类工作 | 阶段, 时段)`：

- **阶段是第二条时间坐标**，不是外部开发流程。它由用户自己的事件序列决定：项目内第几条、距首条多少天、距上条隔了多久。
- **时段仍是强相关的一条坐标**，但改成软条件：阶段证据足够、时段没数据时也能开口，只是置信度打折（`0.6 + 0.4 × 时段置信`）；不会反过来拿两三条规定当「这个点必做」。
- **指令类型**回答「他常在这个阶段收到什么」：修复 / 验证 / 发布 / 回顾 / 新增 / 改动 / 其他。
- **概率会漂移**：近因按 8 周半衰期加权，`trend = 近 4 周占比 − 长期占比`，界面直接标「正在变多 / 变少 / 稳定」。

三张进程表仍属于时间网，不参与项目网 / 事件网的打分，也不读词向量。

### 19.2 阶段与指令怎么判

| 阶段 | 判定（按项目分组、按时间升序） |
| --- | --- |
| 启动 | 前 2 条，或距首条 < 2 天 |
| 推进 | 其余，累计 < 6 条 |
| 打磨 | 累计 ≥ 6 条 |
| 收尾 | 累计 ≥ 10 条且距上条 ≥ 3 天（节奏放缓） |
| 回归 | 距上条 ≥ 14 天后重新出现 |

指令类型取「前缀系列名 + 事件摘要」，按具体词优先、宽泛词垫底的顺序匹配正则（`修复` → `验证` → `发布` → `回顾` → `新增` → `改动`），兜底 `其他`。规则可解释、可改，不引模型。

### 19.3 三张派生表

| 表 | 内容 |
| --- | --- |
| `phase_events` | 每条事件当时所处的阶段、指令类型、项目内序号、距首次天数、距上条天数 |
| `phase_probs` | `P(指令 | 阶段, 时段)`；`weekday=-1/hour=-1` 是不限时段的基线行，其余是精确时段的条件行 |
| `phase_transitions` | 阶段之间的迁移次数、概率，以及迁移发生时的平均序号 / 天数 |

条件行向基线收缩：`weight = (时段近因 + 3 × 基线概率) / (时段总近因 + 3)`。样本少时不会把偶然的两三条放大成规律。`syncTime` 末尾统一重建，纯派生缓存、整体覆盖。

### 19.4 「到什么时候开始需要这类工作」

两个量一起回答：

- `onset_seq` / `onset_days`：该阶段下这类指令首次出现位置的中位数 —— 「这类指令通常从项目第 7 条 / 第 42 天开始」；
- `arrival`：怎么进入当前阶段的迁移 —— 「项目平均走到第 6 条 / 第 35 天，从「推进」进入「打磨」」；`transition` 则给出下一步最可能去哪。

`memory_time` 的 `phase` 把这些拼成一句可转述的询问，例如：「『星界』已经走到『打磨』阶段，这个阶段 100% 是『修复』类指令；这类指令通常从项目第 7 条 / 第 42 天开始，当前时段也支持（时间置信 80%）。要不要我先按这个方向起个头？」

### 19.5 接线与界面

- `memory_time` 增 `phase`（当前阶段与询问）与 `phases`（全量概率表 / 迁移表），内置工具与 stdio 同步；`project` 参数可指定项目，省略取最近活跃项目。
- `/api/time` 一并带 `phase` / `phases`；控制台「时间」页新增「进程阶段」面板：当前询问、各类指令的概率条与漂移标记、阶段迁移表、各阶段基线概率。
- 主界面提醒条**优先问阶段**，阶段样本不足才回退到纯时段 `suggest`；接受仍只写进输入框，不自动发送。
- 提示词只在 `memory_time` 真在工具清单里时多写一句：问到「项目现在该做什么 / 这个阶段常收到什么指令 / 走到什么时候开始需要这类工作」用 `phase`，阶段样本不足就直说，不要按通用开发流程替用户推断。

### 19.6 验收

| 检查 | 结果 |
| --- | --- |
| `npm run test:memory` | **33 项全绿**（新增：阶段判定 / 指令条件概率与起始点 / 迁移 / 近期漂移 / 样本不足不开口） |
| `npm test` | 28 项全绿 |
| `npm run probe:net` | 全绿，三网体检带 `phaseEvents` / `phaseProbs` / `transitions`，`phase` / `phases` 经渲染层可调用 |
| `npm run probe:starmap` | **15 项全绿**（GUI），新增「进程阶段面板渲染」 |
| `npm run probe:roles` / `probe:super` | 全绿，身份与直连会话无回归 |

### 19.7 边界

- 阶段是启发式规则（序号 + 节奏），不是从事件语义里读懂的项目状态；换成模型判定需要另付成本。
- 指令类型是关键词分类，跨语言 / 黑话会落到「其他」；前缀系列名是主要依据，建议写事件时保持前缀语义稳定。
- 漂移只比较「近 4 周占比 vs 长期占比」，不建模季节性或周期性；趋势标记是提示，不是预测。
- 阶段样本 < 3 条时 `phase` 明确返回 `found: false`，不硬编询问。

## 20. 回忆改走权重网 + 单星权重位图（2026-11-10，十七轮）

用户往回看时提出两点：**调用以前的情况不再依靠回忆文件，而是看权重网和「它什么时候触发的」**；以及**点击某个项目或事件时，要能单独打开它的位图**，看到权重近的有哪些、远的有哪些，而不只是一张主星图。

### 20.1 回忆不再拉文件

| 之前 | 现在 |
| --- | --- |
| `memory_context` / `memory_get_context` 组装「全量项目 + 最近 20 条事件正文」的临时上下文包 | 只给常驻硬性上下文、最近活跃的少数项目、权重近/远邻居、最近触发时间；`events` 返回空数组 |
| `memory_recall` 把项目、事件摘要、可复用做法全拼进文本 | 默认 `brief`：文本只有命中项目的权重、最近触发时间、权重近/远邻居；事件与做法仍作**结构化结果**返回，不进文本 |

`memory_recall` 的 `mode=full` 才恢复旧的拼正文行为，`near` 可调整近/远分界（默认 **0.25**，词法权重上限约 0.75，这个分界能把「明显同类」和「只是沾边」分开）。工具描述与提示词都写明：不要改去用 `memory_context` 取全量正文。

### 20.2 「什么时候触发的」

`lastTriggerFor(kind, id)` 按新到旧取四类来源，返回 `{ at, source, label }`：

1. `recall_log` 里最近一次把这个节点回忆出来（**回忆**）；
2. `time_slots` 里这个时段被触发（**时段**）；
3. `phase_events` 里上次推进（**进程**）；
4. 事件本身的时间戳（**事件**）。

时间按本机时区显示。brief 文本里直接写「最近触发 2026-11-10 20:37 回忆」，模型看权重与时间就够判断要不要深挖，不必把正文搬回来。

### 20.3 单星权重位图

- **接口** `/api/nodeview?kind=project|event&id=...&near=...`：以该节点为中心，从 `project_links` / `event_links` 取直接邻居，按权重分成「近」「远」；直接邻居太少时补一层两跳节点（标「经谁连上」），一律算远。每条边带 `percent` 与 `label`（如 `31%`），返回中心、近/远分组、最近触发时间与分界阈值。
- **入口**：控制台点任意项目 / 事件星 → 右侧记录预览头部出现「**权重位图**」按钮；点它切到单星图，工具条出现「**返回主星图**」。位图里的节点也带记录引用，可以逐层点开、单独看它。
- **布局**：中心在原点，权重越高离中心越近；近邻青色内圈、远邻蓝色外圈，图例标出两档数量与分界百分比。**单星图里所有权重线默认就画、线上直接写百分比**，不必先聚焦。
- 修了一个真实取景问题：邻居环绕中心时，全景机位只顾「画面装得下」会让远侧半圈落到相机背后，`project()` 判为不可见，连线和百分比都画不出来。`fitPose()` 现按所有节点旋转后的最小深度设 `depthFloor`，保证没有节点在相机背后。

### 20.4 验收

| 检查 | 结果 |
| --- | --- |
| `npm run test:memory` | **35 项全绿**（新增：上下文无正文 / brief 与 full 分流 / 触发时间 / 单星位图近远分组与百分比 / `/api/nodeview`） |
| `npm test` | 28 项全绿 |
| `npm run probe:net` | 全绿，回忆链路改为 brief 后仍只命中相关项目 |
| `npm run probe:starmap` | **17 项全绿**（GUI），新增「单星位图」与「可返回主星图」 |
| `npm run probe:roles` / `probe:super` | 全绿 |

### 20.5 边界

- 近/远是**边权分档**，不是语义上的「相关 / 无关」；默认 0.25 是拍的，真实数据跑一段后可调。
- 两跳节点只是「经谁连得上」，权重是路径乘积，不等于它和中心真的相似；界面上明确标了「两跳 · 经 X」。
- `memory_context` 工具名保留（避免破坏旧调用），但已不再返回事件正文；依赖它拿历史细节的旧链路要改用 `memory_recall(mode=full)` 或数据表。
- 触发时间取的是最近一次，不列完整触发历史；要看流水请查 `recall_log` / `phase_events` 表。

## 21. 探子模型、观察通道与桌面操控调研（2026-11-10，十八轮）

用户本轮三件事：① 重做「探子」——快速扫描本机项目文件，总结后发给超级智能体，超级智能体编辑后转成权重图存进权重体系；② 超级智能体后续接触更多信息（例如工作聊天记录），据此决定怎么帮用户，典型例子是「今天说想吃火锅 → 到饭点问要不要提前点一份」；③ GitHub 上有能让模型操作应用程序的开源项目，「先看一下」。

### 21.1 探子：只读采集，不碰个人目录

新模块 `electron/scout.js`，职责只有**在用户明确指定的项目目录里只读扫一遍文本文件**，产出可编辑的 `digest`。硬边界：

- 必须显式传 `rootPath`；空值直接拒绝，绝不默认扫桌面 / 下载 / 文档；
- 整个 Desktop / Downloads / Documents / AppData / Library 等个人目录本身被拒绝（其下的具体项目目录仍允许）；
- 跳过 `node_modules` / `.git` / `dist` / `build` / `vendor` / 隐藏目录；不跟随符号链接；每个文件 `realpath` 后校验仍在根目录内；
- 单文件 256KB、总量 2MB、最多 60 个文件、递归 6 层的硬上限；
- 只读，不创建 / 改写 / 移动任何文件；输出的是摘录与统计，不是文件副本。

**工作聊天记录不在探子里**。它属于敏感个人数据，只能经「观察」通道由用户 / 超级智能体显式写入；探子不会自己去翻聊天记录或消息数据库。

### 21.2 摘要 → 超级智能体 → 权重图

链路（每一步都可由用户中断）：

```
scout.scan(root)  →  可编辑 digest
   → 「交给超级智能体整理」：写进直连会话输入框，附严格 JSON 指令
   → 超级智能体产出 {"nodes":[{name,summary,events:[...]}]}
   → 贴回探子 → 「写入权重网」
   → store.commitScout：写 projects / events
   → write 自动触发 reindex + syncTime + syncPhase，三张网随之重建
```

- `commitScout` 同时接受纯文本（按当前项目建 1 节点 + 1 事件）与 JSON（批量建节点与事件，节点上限 12、每节点事件上限 8）；
- IPC `astral:scout:scan` 挂 `memory.read`，`astral:memory:commitScout` 挂 `memory.write`（管理员限定）；超级智能体的 `actor` 由主进程注入，不接受渲染层指定；
- 入口放在「项目设置」弹层里（不占顶栏宽度），与已有的「相关项目 · 权重网」并排；
- **不自动调用模型、不自动写库**：整理结果需要用户确认。

### 21.3 观察通道：到点问具体的事

`observations` 表（schema v7）单独存「近期打算」，字段 `at / source / kind / text / weight / meta / used_at`。关键约定：**观察绝不进 `events`**——事件条数会污染时段习惯与周记，也会改变进程阶段。

- 写入：`memory_time` 的 `action=observe`，或内置 / stdio 工具 `memory_observe`（`kind` = meal / task / preference / note）；提示词要求模型在用户说出打算或偏好时记一条，**只记录不执行**；
- 读取：`suggestAt` / `phaseAt` 返回近 24 小时未使用的观察；`observationAsk` 在饭点（11/12/17/18 点）对 `kind=meal` 生成「你今天提到『想吃火锅』，要不要提前帮你点一份？这样到饭点就能先拿到。」；
- 即使时段样本不足（跨周 < 3 周），观察也能让 `suggest` 返回 `found: true, via: 'observation'`；主界面提醒条**优先**用观察询问，其次阶段，最后时段；
- 接受仍只把 `prompt` 写进输入框，绝不自动下单 / 发送 / 改文件。

实测：12:00 写入「今天想吃火锅」→ `events` 与 `time_slots` 数量不变 → `suggest` 返回观察询问；03:00 不触发。

## 22. 24 小时在线与运行中释放上下文（2026-11-10，十九轮）

用户要求：AI 保持 24 小时在线时，**上下文占用完全由用户控制，且运行过程中随时可以释放一些上下文**。

### 22.1 口径

「在线」由三件事托底，本轮不新增服务器：应用常驻（会话自动落盘、重启恢复）、任务调度器常驻（`jobs.js`）、时间网到点询问。真正缺的是**运行中可控的上下文**——此前只有「分层开关」（下一轮生效的结构性开关）和「预算压缩」（超预算自动把旧消息折成摘要），没有「把某条内容当场放掉」的动作。

### 22.2 释放 ≠ 撤回 ≠ 压缩

| 动作 | 历史记录 | 下一轮上下文 | 适用 |
| --- | --- | --- | --- |
| 撤回 | **删除**该条及后续 | 不出现 | 写错了、发错了 |
| 预算压缩 | 保留 | 折成一行摘要继续带 | 自动兜底 |
| **释放（新）** | **保留**（变淡标记「已释放」） | **彻底不出现，连摘要都不进** | 内容还有用但不需要模型再看 |

### 22.3 实现

- 新纯函数模块 `app/js/context-release.js`（`isContextReleased` / `toggleContextRelease` / `liveMessages` / `releasedStats`），无 DOM 依赖、可单测。
- 两条发送链路同步过滤：项目会话的 `transcriptBlock`（`orchestrator.js`）与直连会话的 history 装配（`superagent.js`）都跳过 `ctxReleased` 的消息。
- **消息操作条**新增「释放 / 恢复」按钮（用户消息与 AI 回复都有，直连会话也有）；释放后消息变淡、左侧虚线、标「已释放 · 不占用上下文」，随时恢复。
- **顶栏用量环**弹层新增「现场释放」区：逐条列出最近 8 条（谁 · 预览 · 估 tokens · 释放/恢复），显示「已释放 N 条 · 省 ≈X tokens」；批量「释放更早（留最近 4 条）」与「全部恢复」。释放后用量环立即重画。
- 用量环同时修正了直连会话口径：以前直连模式数的是项目消息、系统提示词按编制成员算；现在直连模式统计超级智能体自己的消息与它真正的系统提示词。
- `ctxReleased` 作为普通字段随会话存档（项目会话 / `super-agent/session.json`），重启后释放状态原样恢复。
- 释放只改「发给模型的内容」，不改任何存档语义；模型本身收不到任何「有东西被藏起来了」的提示。

### 22.4 与 24 小时在线的配合

长会话里上下文膨胀有三个出口，全在用户手上：结构层关掉（15 层开关）、预算压住（token 上限 + 历史条数）、运行中放掉（本轮的释放）。三层叠加时，无论在线多久，每一轮实际发出的内容都可见（用量环 + 释放面板）、可预算、可回收。

### 22.5 验收

| 检查 | 结果 |
| --- | --- |
| `npm test` | **31 项全绿**（新增：释放退出上下文 / 恢复 / 序列化往返 / 空值） |
| `npm run test:memory` | 37 项全绿 |
| `npm run probe:super` | 全绿：直连会话渲染链路挂上新模块无 ESM 回归 |
| `npm run probe:roles` | 全绿 |

### 22.6 边界

- 释放的粒度是**整条消息**（含该消息的附件与内嵌内容）；派单卡（plan）与工具日志不提供释放——它们本来就不进转录。
- 释放不通知模型：模型不知道某条被放掉，可能出现「它问起被释放的内容」的情况——这是刻意的（诚实优先于隐瞒技巧），需要时恢复即可。
- `estimateTextTokens` 是估算，与供应商计费口径可能有偏差；释放省下的量按同一估算口径显示。

## 23. 知识网：让知识库也有权重（2026-11-10，二十轮）

用户要求：**知识库也要有权重**；底层模型调用知识库时能按权重调用、或自行搜索调相应知识，从而在日益庞大的知识库里不花庞大上下文。

### 23.1 口径：缺的不是检索，是权重

此前知识库只有两条路：`kb_guide` / `kb_search` 每次读全部分册、按 IDF 打分；`inject` 把总纲全文（约 1.4k 字）加三条完整条目（每条约 300 字）塞进系统提示词。库越大，两件事同时恶化——检索变慢、每轮固定成本变高。

词频能回答「哪条和这句话像」，回答不了「哪条更该先看」：一条踩过的坑可能半年没用到，但比昨天随手记的一条重要得多。所以知识需要和项目、事件、时段一样的**自身权重**，并且这个权重必须由真实使用长出来。

### 23.2 第四张网

| 网 | 回答的问题 | 主表 |
| --- | --- | --- |
| 项目网 | 做过什么、和谁像 | `project_terms` / `project_links` |
| 事件网 | 说的是不是同一件事 | `event_terms` / `event_links` |
| 时间网 + 进程层 | 什么时候做、走到哪一步 | `time_slots` / `phase_probs` |
| **知识网（新）** | **这件事该怎么做** | **`kb_nodes` / `kb_terms` / `kb_links` / `kb_hits`** |

正文仍然是项目里的 Markdown（人可读、可随 git 提交、可离线带走），SQLite 只存**索引与权重**。`PRAGMA user_version` 7 → 8。

### 23.3 权重公式（可解释、可回滚）

```text
weight = trust × freshness × (0.55 + 0.45 × precision) × completeness
```

| 因子 | 含义 | 取值 |
| --- | --- | --- |
| `trust` | 谁写的 | 用户手写 1.0 / 全局知识 0.95 / 自动摘要 0.7；再按「有用−没用」反馈 ±0.3，夹在 0.3–1.2 |
| `freshness` | 多久没被用过 | `0.5^(天数/90)`；「避错」半衰 **180 天**——踩过的坑不该那么快过期 |
| `precision` | 搜出来之后有没有真被用 | `(打开+引用+1) / (有效 + 噪声×0.25 + 2)`，噪声 = `max(0, 曝光 − 有效×2)` |
| `completeness` | 四段写全没有 | 0.4 打底 + 标题 0.1 + 触发 0.15 + 步骤 0.15/0.05 + 依据 0.1 + 症状/验证 0.05 |

`precision` 的系数 0.25 是刻意压小的：曝光只是「有机会被看见」，不是「被拒绝」。零曝光给 0.5 中性值，不奖不罚；30 次曝光零打开才降到 0.10。**真正判死刑的只有明确反馈**。

实测曲线（方法条目、完整度 0.95）：零曝光 74% · 曝 8 用 1 71% · 曝 10 用 0 62% · 曝 10 用 4 85% · 曝 30 用 0 57% · 90 天没用 40%（避错 60%）。

### 23.4 检索：相关度 × 权重，两者不可互相替代

```text
score = relevance^0.75 × (0.55 + 0.45 × weight) × 字段加成
```

- `relevance`：`kb_terms` 归一化向量与查询的点积，**候选只从倒排取**（`JOIN kb_nodes` 带作用域条件），不扫全表；
- `relevance^0.75`：略压相关度，让弱相关也能进候选，不至于一条都不给；
- `(0.55 + 0.45 × weight)`：权重最多把分数砍掉 45%——同等相关时决定谁先，不允许把相关的那条压到不相关之下；
- 字段加成：标题命中 ×1.3、摘要命中 ×1.15（标题就是这条知识的适用场景）；
- 邻居扩散：`kb_links` 上取一条最强边带 0.2 衰减，只带一跳；
- MMR 去冗余（λ=0.7）：同一本书 / 同一领域的条目不会占满名额。

### 23.5 渐进披露：三层，默认只到第二层

| 层 | 入口 | 返回 | 典型成本 |
| --- | --- | --- | --- |
| 目录 | `kb_digest` / `memory_kb digest` | 条数、领域分布、权重 top 8、冷条目（从没打开且放了半个月以上） | ≈150 字 |
| 命中 | `kb_guide` / `kb_search` | **编号 + 标题 + 一行摘要 + 权重%**，不含正文 | 每条 ≈40 字 |
| 正文 | `kb_get` | 完整四段，同时记一次「打开」 | 每条 ≈300 字 |

`detail: true` 可以一次要回正文（老调用方兼容）。**注入被压到 151 字**：只留「怎么用 + 现在最该看的三条标题」，正文一律按需取——这条把「上下文随库增长」砍成了固定成本。

### 23.6 学习闭环

| 行为 | 记什么 | 影响 |
| --- | --- | --- |
| 检索命中 | `exposures++` | 只在「远多于使用」时降权 |
| `kb_get` 取正文 | `opens++`、`last_open_at` | 升权 |
| 注入 / 回忆引用 | `uses++`、`last_use_at` | 升权（摘要就够用时也会被算作被用上） |
| `kb_feedback` | `good++` / `bad++` | 立即改权重 |

### 23.7 同步与作用域

- `kb-index.sync()` 是**按作用域对齐**：一个项目一个作用域（`kb:<projectId>`），全局知识单独一个（`global`）。只删「本作用域内有、这次没给」的条目，别的项目不受影响。
- **按 hash 短路**：正文没变就不重建词向量；全部没变时连连线都不重算。
- 词向量的 idf 在作用域内一致（重建时整作用域一起算），保证同项目内分数可比。
- `kb_add` / `kb_update` / `kb_remove` 之后**立即重建**：刚写的必须马上能搜到，删掉的必须马上消失（否则会推荐一条打开就 404 的知识）。
- service 层用文件签名（分册的 mtime + size）短路，库没变时检索不读任何 md 文件。

### 23.8 调用入口

| 入口 | 给谁 | 能力 |
| --- | --- | --- |
| `kb_guide` / `kb_search` / `kb_digest` / `kb_get` / `kb_feedback` | 项目内执行层 | 索引 + 文件正文，`detail` 可一次取全 |
| `memory_kb` | 超级智能体 | 只看索引：`digest` / `search` / `get` / `use` / `feedback` / `map`；正文归项目知识库的 `kb_get` |
| `memory_recall` | 超级智能体 | 回忆里的知识条目只给「标题 + 权重 + 摘要」，不再拼正文（`mode=full` 也一样） |
| 控制台「知识网」 | 用户 | 四个 KPI、权重最高、冷条目、最近检索流水；星图新增「知识网」节点可直达 |

| 检查 | 结果 |
| --- | --- |
| `npm run test:memory` | **40 项全绿**（新增 3 项：摘要/正文分层与打开升权、光搜降权与反馈、作用域同步与删除跟随） |
| `npm test` | 31 项全绿 |

### 23.10 边界

- 权重是**慢变量**：新库所有条目都在 74% 附近，要真实使用几天才会分化。这是刻意的——没有行为数据时不应该假装知道哪条更重要。
- 中文按二元组切，不做语义：「打包失败」搜不到只写了「构建报错」的条目。接 embedding 只需替换 `vectorsFor()`，排序与扩散逻辑不动。
- `completeness` 只看「四段写全没有」，不看写得对不对；写得全但写错的条目仍会被高估。
- 冷条目只是**展示**，不自动删除：删不删是用户的决定。
- `memory_kb get` 不返回正文（超级智能体没有项目文件上下文），要正文走 `kb_get`；这条分工写在工具描述里。

## 24. 消息接入：一套接口，六种渠道（2026-11-11，二十一轮）

用户要求：微信个人号、QQ 个人号、企业微信**都要留好接口**，让用户自己选。

### 24.1 口径：渠道是易耗品，收件箱是资产

平台会改接口、会封号、会下架工具，唯一能沉淀的是「消息进来之后怎么处理」。
所以把两件事彻底分开：

- **适配器**只负责拿到，并翻成统一形状；
- **收件箱**负责去重、分流、落库、决定要不要打扰。

结果是加一种渠道不用改数据库、不用改界面、不用改分流规则——这既是「留接口」的具体含义，
也是这套东西唯一的长期价值。

### 24.2 六种渠道（catalog.js 里的一张表）

| 渠道 | 传输 | 风险 | 能拿到 | 代价 |
| --- | --- | --- | --- | --- |
| `wechat-personal` 微信个人号 | local-db | 只读 | 全部历史与群聊 | 逆向；需外部桥接（命令或 chatlog） |
| `wecom` 企业微信 | callback | 官方 | 单聊（群聊需会话存档） | 需企业认证，群聊按坐席付费 |
| `qq-personal` QQ 个人号 | websocket | 有风险 | 实时全量，能发 | 协议注入，封号风险 |
| `qq-official` QQ 官方机器人 | websocket | 官方 | 群内 @、单聊 | 需审核；群主动推送要群主开 |
| `notify-relay` 手机通知转发 | http | 官方 | 通知栏那一行 | 没有上下文 |
| `webhook` 通用 Webhook | http | 官方 | 任意 JSON | 要自己接 |

每种渠道声明 `capabilities`（能收 / 能发 / 有历史 / 实时 / 认 @）与 `risk`（safe / caution / risky）。
界面按这两个字段渲染，用户一眼能看出「这条能给我什么、代价是什么」，而不是被文案糊住。

### 24.3 数据：schema v8 → v9

| 表 | 作用 |
| --- | --- |
| `inbox_channels` | 渠道登记：类型、开关、配置、状态、增量游标 |
| `inbox_messages` | 原文，主键是去重哈希 |
| `inbox_threads` | 每个会话一行：总量、未读、提醒数、最后一条 |

原文**永不进上下文**。越界的只有三样：`observations` 里的摘要、`inbox_threads` 的索引、
以及一句「要不要问你」。

只有 `alert` / `observe` 写 `observations`——和上次观察通道同理，归档的群聊绝不能影响时段权重。
intake 来源的观察只保留最近 600 条，再多就把饭点提醒挤成噪声。

### 24.4 分流：分档靠「有没有人在叫你」，不靠分数

```
alert     有人在叫你（@ / 点名 / 关键词 / 在吗尽快速回），且分数 ≥ 60
observe   其余有信号的（约时间、托办事、吃喝），分数 ≥ 22
knowledge 像一条经验（踩坑、报错、别用），分数 ≥ 12
archive   其余
```

群里一堆闲聊能凑到 68 分也不弹窗——只要没人叫你。这条是「会不会变成骚扰源」的分水岭。

### 24.5 去重：同一条消息只该记一次

`sha1(渠道 + 会话 + msgId + 分钟 + 发送人 + 正文前 64 字)`。

有 `msgId` 时不用时间；没有 `msgId`（转发、告警）时把时间压到分钟——同一分钟重复推只算一条，
跨分钟仍算两次。第一版没压分钟，结果同一条告警推两次就各算一条，权重被自己刷高。

### 24.6 本地入口

单个 HTTP 服务，默认 `127.0.0.1:45890`，路由 `POST /hook/:渠道id`。

- 默认只绑回环；渠道勾了「允许局域网」才绑 `0.0.0.0`。
- 令牌自动生成，`?token=` 或 `X-Astral-Token` 都认；比较用 `timingSafeEqual`。
- 企业微信走自己的验签与 AES 解密（WXBizMsgCrypt，补位块 32 而非 16，Node 默认 PKCS7 会解出乱码）。

### 24.7 微信个人号：只定义桥接，不打包解密

四种做法里只有一条值得走：读本地库。它不联网、不登录、不发消息，微信服务端不知道，
所以不会触发风控；代价是属逆向、大版本升级会断。

我们**不内置 SQLCipher 解密**：那套细节随微信版本变，硬编进来会变成「升级即失效且没人看得懂」。
改成桥接契约：

- `command`：`<命令> --since <ISO>`，stdout 每行一条 JSON；
- `chatlog`：指向本机已跑起来的 chatlog HTTP 服务。

换工具不用改这里，也不替用户分发任何来路不明的二进制。

### 24.8 工具与界面

| 入口 | 用途 |
| --- | --- |
| `memory_inbox`（MCP） | 超级智能体看「外面发生了什么」：recent / search / threads / stats / handled |
| 设置 → 消息接入 | 渠道卡片、开关、配置弹层、接收地址、收件箱预览 |
| `astral:intake:*`（IPC） | 渲染层与主进程之间的通道，共 11 个 |

### 24.9 验收

| 检查 | 结果 |
| --- | --- |
| `npm run test:memory` | **43 项全绿**（新增 3 项：入库幂等与分流、渠道契约与密钥、解析与令牌） |
| `npm test` | 33 项全绿 |
| `npm run probe:intake` | **17 项全绿**（数据 12 + 界面 5，含截图） |
| `npm run doctor` | 与打包版一致 |

### 24.10 边界

- **默认全部关闭**。接进来是要用户点头的事，不能装完就开始读消息。
- 企业微信只能稳拿单聊；群聊要开会话存档并付费，这条写在卡片上，不藏。
- QQ 个人号有封号风险，卡片上直接写「务必用小号」，不粉饰。
- 微信个人号的图片（4.x AES）没有公开解法，只存占位。
- 手机通知转发只有那一行字，没有上下文——它的定位是触发器，不是消息源。
- 代发默认关闭。发出去收不回来，这个能力留着接口，但不默认打开。

## 25. 安全边界：出站守卫与工作留痕（2026-11-11，二十二轮）

前二十四节解决的是「记得住、找得到、收得进」，这一节解决「敢不敢用」。

用户提了两个具体的怕：一是别的渠道让 AI 发东西，里面夹着隐私或 API 密钥；
二是领导在群里派的活，做完出了事说不清是谁让做的。
对应两套装置：**往外走的过闸门，往里进的进账本**。

### 25.1 两个场景不要混

| | 出站 | 派活 |
| --- | --- | --- |
| 装置 | `security_gates` 闸门 | `security_tasks` + `security_ledger` |
| 默认 | 命中就问；密钥级默认「不发」 | 不记账，等用户点头 |
| 用户看到 | 「这段内容要发出去吗」 | 「这像派活，要不要留痕」 |

共用一条原则：**决定权在用户，装置只负责把决定记下来。**
它不替用户判断该不该发，也不替用户判断这活该不该接。

### 25.2 闸门：什么算出站

| 场景 | exposure | 处理 |
| --- | --- | --- |
| 内置工具（读写文件、查记忆、截屏） | `none` | 不问。写自己硬盘不是外泄 |
| 外部工具，名字像发 / 传 / 提交 / 建工单 | `send` | 命中就问 |
| 外部工具，名字像列 / 查 / 读 / 搜 | `pull` | 只在密钥 / 身份级命中时问 |
| 外部工具，名字认不出来 | `unknown` | 按 `send` 算 |

先看动词再看名词：`list_issues` 是拉取，`create_issue` 才是往外写；
名字里同时带 `send` 一类动作词的，一律按能发算——宁可多问一次。

### 25.3 识别：宁可漏一点噪声，不要天天误报

误报比漏报更毁这件事。一天弹二十次确认，第三天用户就闭眼点允许，边界等于没有。
所以每条规则都带一个「不报」的对偶条件：

- 身份证 18 位**且校验位算得过**（否则订单号天天报警）；
- 银行卡 16–19 位**且 Luhn 通过**（全同数字直接排除）；
- 疑似密钥串必须**至少两类字符、非纯 hex、前后 48 字内有 key/token/密钥**——
  git 哈希每天出现几十次，一律不报；
- API 密钥只认厂商前缀（`sk-` `ghp_` `AKIA` `AIza` `xoxb-` `glpat-` `sk_live_`…），
  前缀是厂商给的，几乎不会误。

级别：私钥 / API 密钥 = 密钥级，口令 / 身份证 / 银行卡 = 高危，
手机号 / 高熵串 = 敏感，本机路径 = 轻微（只提示不拦）。

放行规则只有一句话：**不出去的不问，只取不送的不问，中低风险且在放行期内不问，其余都问。**
「这类不再问」对密钥级与高危**不开放**——可以容忍「手机号这半天别问了」，
不能容忍「API 密钥这半天随便发」。

### 25.4 批准绑在指纹上，AI 拿不到凭据

```
digest = sha256(kind | target | 正文或参数规范化 JSON)
```

- 批准一次 = 这个指纹 30 分钟内可用一次，用掉即作废；
- 改一个字、换一个群、换一个工具，指纹就变了，重新问。

这样不需要把批准令牌发给 AI：AI 手里没有凭据可偷，它只能「再检查一次」，
而检查会去库里找有没有同指纹的批准。

**闸门表不存正文**，只存指纹、脱敏预览（`sk-pro…Yz`）和命中清单。
为了安全先把用户的密钥收一遍存起来，是这类功能最容易闹的笑话；
数据库被拖走时，攻击者最多知道「某人曾试图发一个 sk- 开头的密钥给产品群」。

### 25.5 留痕：候选不写账本

```
消息进来 → 分流为 alert → 像派活？ → 建候选（账本为空）
                                      ↓ 用户点「开始留痕」
                                  账本第 1 条：来源 / 原话 / 时限
                                      ↓ 每做一步 append
                                  动作 / 拦下 / 批准 …
                                      ↓ 做完
                                  最后一条：归档（结果 / 证据位置）
```

「像派活」的判断放在**分流层**（`intake/normalize.js`），因为它本来就是
「这条要不要打扰你」的一部分：@ 你 + 动作词 + 时限。生活琐事（带饭、取快递）
词表单独扣分；群里没点你的活不算你的活。

候选阶段账本一条都没有——留痕是用户的决定。被丢掉的候选只留一个 `dropped` 状态，
证明「当时问过、你说不用」。

### 25.6 账本只追加的两道锁

1. **数据层**：`security_ledger` 上的触发器直接 `RAISE(ABORT)` 掉 `UPDATE` / `DELETE`；
2. **数学层**：每条的 `hash = sha256(prev_hash + "|" + 规范化 JSON)`。

改一行，它自己的哈希对不上；删一行，下一行的 `prev_hash` 接不上。
`verify()` 从头重算整条链并报出第一个断点，不抽样、不信任索引。
写错了就追加一条 `correct`，不是改上一条——这是账本，不是文档。

### 25.7 存证能证明什么，不能证明什么

**能**：某条消息在某个时刻、从某条渠道、由谁发出，原文如此；某个动作由 AI 执行、
参数是什么；某次外发得到过用户明确批准（或没有）；这份记录自建立以来没被改过。

**不能**：记录**完整**（没开留痕就是空的，它不会替你补）；原话的绝对真实性
（那需要平台侧存证）；法律责任的划分（它是证据材料，不是判决）；附件里写了什么。

这几条写进导出件，也写在设置页。喊「放心」没用，说清边界才有用。

### 25.8 工具与界面

| 入口 | 用途 |
| --- | --- |
| `security_check`（MCP） | AI 外发前自检：`screen / pending / stats / policy`；`verdict=confirm` 就停下来问人 |
| `security_ledger`（MCP） | `tasks / open / append / close / ledger / verify / export` |
| 主进程工具调用 | 外部工具执行前过闸门；命中弹原生确认窗，**默认按钮是「拒绝」** |
| 设置 → 安全边界 | 待确认队列、留痕、账本、校验、导出、两个开关 |
| `astral:security:*`（IPC） | 10 个通道；`decide` 只认主窗口 sender |

**「完全授权」跳不过闸门。** 工具授权回答「这个工具能不能用」，闸门回答
「这段内容能不能出去」——两件事。`permissions.full = true` 的用户照样会在
密钥外发时被问一次。**AI 也不能批准自己**：`approve` / `deny` 只存在于主进程 IPC。

### 25.9 验收

| 检查 | 结果 |
| --- | --- |
| `npm run test:security` | **27 项全绿**（识别 7 / 放行 4 / 闸门 6 / 留痕 4 / 账本 2 / 门面 4） |
| `npm run test:memory` | 43 项全绿（分流新增「像派活」信号后无回归） |
| `npm test` | 33 项全绿 |
| `npm run probe:security` | **15 项全绿**（数据 8 + 界面 5 + 控制 2，含截图） |
| `npm run doctor` | app / electron 共 154 个文件与打包版一致 |

关键断言：库里搜不到完整密钥；批准后改一个字要重新问；`UPDATE` / `DELETE` 被
触发器拒绝；故意绕过触发器改一行后 `verify()` 精确报出断点（`brokenAt = 2`）。

### 25.10 边界

- **看不见工具自己去读的文件**。参数只有路径时，闸门不知道文件里有什么。
- **不做 OCR**：截图、图片里的密钥拦不住。
- **用户自己手动发的不拦**。那是他本人的决定，不是 AI 的决定。
- **放行期内的同类内容不再问**。这是用户选的，8 小时后自动恢复。
- **账本证明「没被改」，不证明「都记了」**。留痕要开、要人点头。
- 默认开守卫、开留痕候选，但**不默认弹窗**：只在你真的要被问到的时候出现。

## 26. 留痕压缩进事件网与按权重追原委（2026-11-11，二十三轮）

第 25 节让留痕能「记下来、改不了」，但账本不能直接拿去回忆：一件活几十条，
全塞进上下文等于没做压缩。这一节解决三件事：**账本压成事件、安全状态进首流、
追责时按权重和时间还原原委**。

### 26.1 两份材料，各干各的

| | 账本 | 事件 |
| --- | --- | --- |
| 给谁看 | 追责、导出、校验 | AI 回忆、权重排序、首流 |
| 体量 | 一条不留 | 一件一行，`summary ≤150` + `result ≤120` |
| 索引 | 只按任务 | 进事件网，可被检索、可连边 |
| 修改 | 触发器禁改禁删 | 可合并、可重建 |

归档（`close`）即压缩，`digest` 可手动补压。同一任务账本长出新的条目后可以再压，
追加下一条；没新增就幂等返回原事件。

### 26.2 压缩规则

```
summary = 谁（渠道·会话）：原话前 62 字 → 结果前 42 字
result  = 动作 n · 外发 n · 批准 n · 拦下 n · 账本 n 条 · 证据 A-…
```

- 先过 `sensitivity.redactText` 再落库：事件会被检索、会进上下文，
  留痕不能反过来成为泄露渠道。
- 前缀 `LZ`、系列「工作留痕」、`project_id` 为空（跨项目）。
- **不进时间网**：`syncTime` 明确排除 `prefix = 'LZ'`，避免作息里多出一个
  只在出事时才出现的系列。

### 26.3 首流

`hard-context.promptText()` 末尾追加 `### 安全状态（实时）`，由
`security/brief.js` 直接读三张表生成，上限 260 字：

```
- 待你点头 1 件：密钥级·产品群
- 在办 2 条：A-20261111-01 把方案整理…
- 已归档 5 条，进事件网 3 条
- 问原委：security_ledger action=trace id=A-20261111-01
```

四块硬性上下文的 3600 字预算不动；这一块单独计量，不搬账本正文。

### 26.4 权重

```
weight = (0.42 + 0.58·evidence) × (0.6 + 0.4·integrity)
       × (0.65 + 0.35·severity) × (0.7 + 0.3·freshness)
```

`evidence = 1 - 0.5^(条数/5)`；`freshness` 半衰 120 天；
`integrity = 0.35 + 0.35×批准覆盖率 + 0.2×已归档有结论 + 0.1×已进事件`；
`severity = 0.25 + 0.18×min(2,拦下次数) + 0.25×是否密钥级`。

与知识网同一套写法：因子相乘、可解释、可回滚。实测空候选约 23%，
6 条账本 + 1 批准 + 1 拦下约 60%，同样的记录放到 240 天前约 43%。

### 26.5 追原委

`security_ledger action=trace`：有编号用编号，没有就按一句话找。

- **问原委时按权重与时间，不要求字面重合**：用户说的是「谁让我改合同的」，
  原话里可能只有「合同」。普通问法仍只认内容，避免把所有留痕都翻出来。
- 相关事件三样加权：事件网连边 0.5 + 内容重合 0.3 + 时间接近 0.2，
  窗口默认前后 12 小时。
- 输出六段：来路 / 做了什么 / 结果 / 证据 / 同一时间前后 / 要留意。
  按时间排，不按重要度排 —— 追责看的是先后。
- 记录缺口照实说：账本是空的、没归档、外发与批准对不上、有更正。
- 原文只在这里出现：用户发起的回查，不是日常注入。

### 26.6 接线

| 层 | 改动 |
| --- | --- |
| schema | v10 → v11，`security_tasks` 补 `event_id / event_code / digested_at / last_digest_seq` |
| 计算 | 新增 `security/digest.js`（压缩、权重、重合、意图）、`security/brief.js`（首流） |
| 存储 | `memory/security.js` 增 `digestTask / trace / search / brief`；`closeTask` 在 store 层触发压缩与重建索引 |
| 首流 | `hard-context.promptText()` 追加实时块 |
| 回忆 | `memory_recall` 增加 `security` 段与「【留痕 · 按权重】」文本 |
| 工具 | `security_ledger` 增 `digest / trace`；`security_check` 增 `brief` |
| 界面 | 留痕行显示 `LZ001` 标签与「看原委 / 压进事件」按钮；原委弹层可复制、可转导出 |
| IPC | `astral:security:task` 增 `digest`（写）与 `trace`（只读，`memory.read`） |

### 26.7 验收

| 检查 | 结果 |
| --- | --- |
| `npm run test:security` | **37 项全绿**（新增 10：压缩 3 / 首流 1 / 权重 1 / 搜索 1 / 原委 2 / 回忆 1 / 时间网 1） |
| `npm run test:memory` | 43 项全绿（schema v11、31 张表不变） |
| `npm test` | 33 项全绿 |
| `npm run probe:security` | **21 项全绿**（数据 12 + 界面 7 + 控制 2，含截图） |
| `npm run doctor` | app / electron 共 156 个文件与打包版一致 |

关键断言：归档后事件网多一条 `LZ001`、账本仍是原来的条数；原话里的密钥不出现在
事件表；账本没新增时重复 digest 返回同一条；问「谁让我改合同的」能命中并给出
「原委 + 内容」的理由；240 天前的同等记录权重低于今天。

### 26.8 边界

- **事件是压缩件，不是证据**。要拿去说事，导出账本，不要拿事件摘要当存证。
- **没开留痕就没有原委**。trace 会明说「账本是空的」，不补故事。
- **只压留痕，不压聊天**。收件箱原文仍然不入上下文。
- **权重是排序，不是判决**。它决定先看哪条，不决定谁该负责。

## 27. 接入状态进首流，工具交给超级智能体（2026-11-11，二十四轮）

第 24 节把渠道接通了，但只是「能收」。用户拨开开关以后，超级智能体并不知道
自己在听——这等于摆了一台没接线的电话机。这一节解决三件事：
**让它知道在听、知道外面有没有人等它、知道去哪儿取原文**。

### 27.1 一块 240 字的常驻文本

```
### 消息接入（实时）
- 已接 1 条渠道：企业微信（运行中 1）
- 外面有 1 条在等你：张经理 小王，明天下午三点前把方案整理一份发我
- 今日 1 条（提醒 1 · 观察 0 · 知识 0 · 归档 0）
- 取全文：memory_inbox action=recent route=alert；哪个群最热：action=threads
```

由 `electron/intake/brief.js` 直接读三张收件箱表生成，插在安全状态之前，
**不计入四块硬性上下文的 3600 字预算**（和安全块一样单独计量）。

### 27.2 四条取舍

| 决定 | 理由 |
| --- | --- |
| 没开渠道返回空串 | 不为「未开启」付每一轮的成本；空块直接跳过 |
| 最多两条 alert 的一句话 | 群聊再热闹也只占两行，原文留在库里按需取 |
| 起不来的渠道单独点名 | 用户问「怎么没收到」时，AI 先看到 `配置不全`，而不是回答「没消息」 |
| 上下文与工具返回同一段 | 两处各写一遍，迟早不一致；`brief` 直接复用同一函数 |

`待启动` 不算故障——被动渠道刚存下来、还没轮到启动时就是它。
真故障是 `启动失败 / 配置不全 / 已停止 / 解密失败`。

### 27.3 必须实时，不能只在启动时取一次

原来的硬性上下文只在启动、以及窗口重新获得焦点时刷新。这意味着：
用户开着窗口聊天，外面来了消息，提示词里还是旧的——那不叫「知道打开了」。

两条触发线：

1. **新消息落库**：`intake.ingest()` 通过 `onIngest` 回调通知主进程，
   主进程 `webContents.send('astral:intake:new')`，渲染层 1.5 秒节流后重取；
2. **渠道变了**：设置页拨开关 / 保存配置 / 移除渠道，派发
   `astral:memory-context-refresh`，走同一次刷新。

节流是必须的：群里刷屏时，每来一条就查一次库没有意义。

### 27.4 工具补两刀

`memory_inbox` 原来只有 `recent / search / threads / stats / handled`，
现在补：

- `brief`：和常驻上下文同款的两三行；
- `channels`：开了哪几条、跑到什么状态、最后一次什么时候；
  只回 id / 名称 / 开关 / 状态，**不回配置**（里面有路径和 URL）。

工具描述也重写了：明确「这是你听外面消息的唯一入口」「有 alert 就该主动告诉用户，
别等着被问」「不要凭印象编」。超级智能体的直连会话边界里也加了一句：
外部消息不在会话里，走收件箱主动取。

### 27.6 边界

- **只报状态，不替用户回消息**。代发要另外过闸门（第 25 节）。
- **首流里没有原文**。要看原话，用 `memory_inbox` 取；要证清白，用留痕账本。
- **没收到就是没收到**。渠道没起来时它明说哪条没起来，不用「可能网络问题」糊过去。
- **AI 不能自己开渠道**。开关只在设置页与主进程 IPC 里，工具层够不到。
